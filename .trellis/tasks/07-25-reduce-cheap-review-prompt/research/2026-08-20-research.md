The template `pr_agent/settings/pr_reviewer_prompts.toml` (v0.39.0) gates

`extra_instructions`, `repo_context`, `require_can_be_split_review`,

This matters for how much reduction is even available: the four `require_*`
flags that are ON by default are the only prompt blocks a profile can switch off,
and the ~180-line output schema shrinks with them because each dropped
requirement removes its schema field too. `extra_instructions` *adds* tokens.
A "reduced" profile is therefore mostly a subtraction exercise over four flags
plus `num_max_findings`, not a prompt rewrite.

### C3. Profile identity, binding, and fail-closed validation are ALREADY BUILT

### C5. This repo's own installation currently routes away from PR-Agent

`.github/sd-github-review.json` is schema v4 with
`configuration.routeMode: "copilot"` and `REVIEW_ROUTE_MODE` marked

## Open Questions

1. **Is the v2 layer in scope for this task at all?** The park rationale (now
   cleared) held that the real blocker is distribution, not missing v2 work.
   C4 says the profile stack exists but cannot run. This task can either (a)
   deliver profiles through the *reachable* path — literally adding
   `PR_REVIEWER__*` env vars to two workflow files, which would satisfy the
   spirit of the PRD in an afternoon but bypass the entire catalog/compiler
   contract, or (b) wait on the adapter integration that makes the v2 path
   live. These are very different tasks. This needs an explicit decision before
   implementation starts.
2. **How is an evaluation baseline produced given C5?** Route mode is `copilot`
   here, so no PR-Agent run happens in this repo. Does evaluation run against a
   scratch repo, a temporarily flipped route mode, or recorded fixtures?
3. **Does the cheap model even work today?** The sibling research
   (`.trellis/tasks/07-25-bound-cheap-review-token-usage/research/2026-08-20-research.md`,
   G3) reports that the configured default cheap model
   `openrouter/qwen/qwen3-coder-30b-a3b-instruct` is absent from PR-Agent
   v0.39.0's `MAX_TOKENS` map with `custom_model_max_tokens` at `-1`, which
   raises before review. If true, no cheap review has ever succeeded on the
   defaults, and any token-reduction measurement is blocked behind that defect.
   Worth confirming against a real run before building an evaluation harness.
4. **Where does the private adapter registry physically live?** The PRD forbids
   prompt values in repository source. Nothing in the repo indicates the
   hosting mechanism for adapter-side values.

## Recommendations

1. **Record the C2 inventory as the deliverable for implement.md step 1** — it
   is now done and should not be re-researched. The actionable subset is small:
   four default-on `require_*` flags, `num_max_findings`, `extra_instructions`,
   and the three cosmetic output flags.
2. **Resolve Open Question 1 before any code.** The gap between "add two env
   vars to a workflow" and "make the v2 layer reachable" is the entire size of
   this task. Given the parent is *cost controls* and 71% of `src/` is
   unreachable, the cheap win is the workflow-level profile; the catalog-bound
   version should be sequenced behind the adapter-integration task that
   currently has no module at all.
3. **Sequence this behind Open Question 3.** Measuring token reduction against a
   baseline that errors out is not measurable. Confirm a successful cheap review
   exists first.
4. **Do not add `extra_instructions` as the primary reduction lever.** It grows
   the prompt. The reduction comes from switching off the four default-on
   `require_*` blocks and their schema fields; `extra_instructions` should be
   used sparingly if at all, and its cost counted against the savings.
5. **When profiles do land, bind the deep lane explicitly too.** AC4 requires
   deep candidates to retain their own explicit profiles; today both lanes are
   equally unbound, so "deep is unaffected" is not currently provable by any
   test.
