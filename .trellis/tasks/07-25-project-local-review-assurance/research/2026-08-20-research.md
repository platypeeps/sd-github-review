### Outcome triple validation exists; outcome→Check mapping does not

`decodeReviewOutcomes` (`src/protocol-v2.js:806-875`) validates a caller-supplied
`{reviewOutcome, assuranceOutcome, gateOutcome}` triple. Relevant invariants:

- `assuranceOutcome.state === "deferred"` is accepted **only** with
  `reasonCode === "budget_exhausted_deferred"` — `:829-833`.
- `localBlocking` (any of the three non-clean local states) cannot coexist with
  `assuranceOutcome.state === "pass"` — `:840-846`.
- Any non-budget failure, including every `localBlocking` state, forces
  `gateOutcome.state === "block"` — `:858-865`.

This is a *validator*, not a *mapper*. Nothing derives the triple from a decoded
`localReviewReceipt`, and nothing derives a Check `conclusion` from the triple.

### Check projection + compare-and-swap

- `decodeCheckProjection` (`src/protocol-v2.js:1324-1345`) validates
  `{checkName, headSha, conclusion, revision, attempt, latestAuthorizedAttemptToken}`.
  The `conclusion` is whatever the caller supplies, constrained only to
  `CHECK_CONCLUSIONS = ["success", "failure", "neutral", "action_required"]`
  (`:157-162`).
- `authorizeProjectionWrite` (`src/protocol-v2.js:1351-1381`) is a pure
  authorizer: initial write must be revision 1 (`:1358-1360`), revision must
  strictly increase (`:1367-1369`), same head requires the presented token to
  match the *current* projection's token (`:1370-1378`), changed head returns
  `changed-head-supersession` (`:1380`). It throws on rejection and holds no
  state; it does not write anything.
- The projection schema carries **no** title, summary, actor, tool/profile, time,
  evidence digest, or trust wording. PRD acceptance criterion 3 has no
  corresponding field anywhere in the tree.

## Gaps vs PRD

Ordered by how much they change the plan.

1. **PRD requirement 3 contradicts the shipped decoder.** The PRD says
   "missing/new-head evidence to **deferred** assurance/block". `decodeReviewOutcomes`
   rejects a `deferred` assurance whose reason is not `budget_exhausted_deferred`
   (`src/protocol-v2.js:829-833`). The shipped fixture for the awaiting case uses
   `assuranceOutcome: {state: "fail", reasonCode: "awaiting_local_attestation"}`
   (`fixtures/protocol/v2/outcomes.valid.json:105-107`), and the parent task's
   own contract mapping says "missing/new-head evidence is **action-required**
   assurance plus a blocking gate"
   (`.trellis/tasks/07-25-support-local-attested-reviews/research/contract-mapping.md`,
   "Accepted Decisions"). Three sources say `fail`/`action_required`; only the PRD
   and `design.md` say `deferred`. **This must be resolved before implementation** —
   see Open Questions.
2. **No outcome→Check mapper.** PRD requirement 3 and acceptance criterion 1 need
   a pure function from a decoded `localReviewReceipt` (or a
   `localAttestationStatus`) to `{reviewOutcome, assuranceOutcome, gateOutcome}`
   plus a `conclusion` per Check. Nothing in the tree does this;
   `decodeCheckProjection` only validates a conclusion the caller already chose.
3. **No Check content model.** Acceptance criterion 3 requires titles/summaries
   exposing actor, exact head, tool/profile, time, result, evidence digest, and
   trust limitation. `decodeCheckProjection` (`:1324-1349`) carries none of these
   fields. The only Check-text builder in the tree, `encodeReceiptCheckText`
   (referenced at `src/receipt.js:141`), is v1-receipt shaped and unrelated.
4. **No writer.** Both PRD requirements 2 and 5 assume something publishes a
   projection. There is no assurance/gate Check writer, so "prevent late writes"
   and "publish a new awaiting-local-attestation projection for the new head"
   have no host. `authorizeProjectionWrite` is a predicate only.
5. **No readiness surface.** PRD requirement 6 and acceptance criterion 4 need a
   readiness path that reports actionable local-attestation setup errors.
   `decodeSetupDiscoveryV2` has no consumer, no branch-protection read exists,
   and `config/routed-review-setup-v1.json` advertises neither Check.
6. **Upstream dependency unstarted.** `07-25-ingest-local-review-attestations` is
   `"status": "planning"` with no branch. Nothing produces a verified immutable
   `localReviewReceipt`, which PRD requirement 1 names as the *only* permitted
   input. This task cannot be integration-tested end to end until it lands;
   it can be built and unit-tested against fixtures.
7. **Privacy assertion is untested at this boundary.** Acceptance criterion 5
   ("no Check path publishes raw findings") is currently vacuous — there is no
   Check path. The `FORBIDDEN_FIELD_NAMES` walker (`src/protocol-v2.js:168+`,
   applied by `rejectForbiddenFields`) gives the mechanism to make it non-vacuous
   once a content model exists.

## Staleness in existing design/implement

Both artifacts are dated July and predate the current tree.

- `design.md` said "the existing revisioned Check writer". **There is no such
  writer** — `src/receipt.js:543` writes only `sd-github-review/receipt`, and
  `authorizeProjectionWrite` is a pure authorizer that writes nothing. Corrected
  in place.
- `design.md` said awaiting local evidence yields "deferred" assurance. This is
  refuted by `src/protocol-v2.js:829-833` and by the parent's contract mapping.
  Corrected in place to the shipped `fail` + `action_required` shape, with the
  asymmetry-with-budget point preserved (that was the paragraph's real intent).
- `design.md` said the design reuses "the same latest-authorized-attempt token
  and compare-and-swap contract as managed recovery". Two divergent CAS shapes
  exist (table above); "the same … as managed recovery" was not true. Corrected
  to name `authorizeProjectionWrite` as the contract this task extends and to
  flag the divergence as a decision to make.
- `implement.md` step 2 said "Reuse revision/CAS projection writes". There are no
  projection *writes* to reuse. Corrected.
- `implement.md` step 5 named `npm test`, `npm run check`, and metadata
  validation. Those still exist (`package.json` scripts, `scripts/validate-action-metadata.mjs`),
  so that step stands; only the wording around what is being verified changed.
- Neither artifact mentioned the installer. Manifest schema is now 4 with
  route mode installer-managed (`scripts/consumer-installer/codecs.mjs:159,171`),
  and `ROUTE_MODES` (`:122`) has no `local-attested` member — a readiness
  requirement (PRD 6) that the July plan did not anticipate. Added to
  `implement.md`.
- Neither artifact is stale about the Check *names*, the gate-only
  branch-protection rule, or the trust wording; those all hold at
  `src/protocol-v2.js:152-155`, `:1413`, and `:1103-1112` respectively.

## Open Questions

1. **Is awaiting-evidence assurance `fail` or `deferred`?** The PRD says
   `deferred`; the code, the fixtures, and the parent's contract mapping say
   `fail` with an `action_required` Check conclusion. Either the PRD text is
   corrected to `fail`/`action_required`, or `decodeReviewOutcomes:827-831` is
   widened to admit `awaiting_local_attestation` as a second sanctioned deferred
   reason. Widening the decoder weakens a deliberate invariant ("proven
   pre-dispatch budget exhaustion is the ONLY failure that may defer assurance",
   `src/protocol-v2.js:826-828`) and would need the parent's sign-off.
   Recommendation: correct the PRD.
2. **Which CAS contract wins?** Extend `protocol-v2.js#authorizeProjectionWrite`
   (pure, throws, stateless) or adopt the `review-deferred-recovery.js` ledger
   reducer shape (stateful, returns rejections, retains late evidence)? PRD
   requirement 5 explicitly wants "retain old receipts, prevent late writes",
   which only the recovery shape currently models via `retainLate`.
3. **Where does Check content live?** Extending `decodeCheckProjection` with
   title/summary fields grows a schema that is currently a pure CAS token. A
   sibling `decodeCheckContent` keeps the CAS surface small at the cost of a
   second decode boundary.
4. **Does this task ship a writer at all,** or only the pure projection contract
   plus fixtures, leaving the GitHub write to whichever task finally wires v2
   into `src/index.js`? The park note in `task.json` argues the real blocker is
   distribution, which suggests the pure-contract scope.
5. **Should `local-attested` become an installer route mode?** PRD 6 wants
   readiness to detect misconfigured local-attestation workflows, but
   `ROUTE_MODES` (`scripts/consumer-installer/codecs.mjs:122`) has no such value,
   so there is nothing for readiness to detect a misconfiguration *of*.

## Recommendations

1. **Resolve Open Question 1 first.** It is a one-word PRD edit or a decoder
   invariant change, and every mapping table in this task depends on it. Do not
   start implementation with the PRD and the code disagreeing.
2. **Scope this task to pure contracts + fixtures**, consistent with every other
   v2 module in `src/`. Deliver: an outcome mapper, a Check content model, and
   the extended CAS — all leaf-pure, all fixture-tested — and leave the GitHub
   write to the distribution task. This keeps the task shippable while
   `07-25-ingest-local-review-attestations` is unstarted.
3. **Reconcile the two CAS shapes explicitly** rather than silently adding a
   third. If `authorizeProjectionWrite` wins, it needs a late-evidence retention
   result; if the recovery reducer wins, `authorizeProjectionWrite` should be
   documented as superseded.
4. **Make acceptance criterion 5 non-vacuous** by running the existing
   `rejectForbiddenFields` walker over any new Check content decode boundary and
   adding a `*.invalid.json` fixture per forbidden field class, mirroring
   `fixtures/protocol/v2/privacy-fields.invalid.json`.
5. **Defer PRD requirement 6's branch-protection half.** There is no branch
   protection read anywhere in the tree; building one is its own task. What this
   task *can* deliver is the descriptor half — advertising the two Checks in
   `config/routed-review-setup-v1.json` — and even that is a schema bump on a
   shipped v1 contract, so confirm before touching it.
