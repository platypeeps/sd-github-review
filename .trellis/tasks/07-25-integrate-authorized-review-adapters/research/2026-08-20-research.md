## 1. Current State

### 1.1 A v1 adapter seam already ships and is reachable end to end

The parent PRD reads as greenfield, but the repository already has a working —
if much thinner — version of the exact seam it describes. It is worth naming
precisely, because roughly half the parent's acceptance criteria are already
satisfied at v1 granularity.

The seam is a three-hop handoff across GitHub Actions jobs:

1. **Emit.** `route` builds a bounded, canonical adapter request from the
   durable receipt — `src/operations.js:141-160` (`adapterRequest()`), gated on
   `result.dispatchAllowed && backend?.kind === "external"` at
   `src/operations.js:414-415`, surfaced as the `adapter-request` output at
   `src/operations.js:204`. It is size-capped at 16 KiB
   (`src/operations.js:28`, enforced `src/operations.js:156-158`).
2. **Execute.** A separate, credential-scoped job runs the third-party
   reviewer — `examples/sd-review.yml:69-159`.
3. **Acknowledge and finalize.** `acknowledge` converts the request plus a job
   outcome into an acknowledgment with no GitHub client at all
   (`src/operations.js:242-259`), and `finalize` folds it into the receipt
   (`src/operations.js:455-485`).

The wire shapes are decoded, not trusted: `decodeAdapterRequest` at
`src/protocol.js:661-727` and `decodeAdapterAcknowledgment` at
`src/protocol.js:728`. `decodeAdapterRequest` re-derives and re-checks
`logicalDispatchId` against the request identity and rejects any
`backend.kind` other than `external` (`src/protocol.js:692`, `src/protocol.js:701`).

The operation set itself is declared once and shared by runtime, metadata
validation, and tests: `src/operation-contract.js:26-132`. `acknowledge` is
declared `needsClient: "no"` with `permissions: {}`
(`src/operation-contract.js:95`, `src/operation-contract.js:101`), and any
semantic payload input belonging to another operation is actively rejected
(`src/operation-contract.js:245-259`, enforced at `src/operations.js:267-273`).

### 1.4 The structural blocker: the dependency-boundary matrix forbids the wiring

`test/dependency-boundaries.test.js:18-55` freezes the complete allowed-import
matrix. The two entrypoint-side modules are:

- `operations.js` may import only `protocol.js`, `router.js`, `receipt.js`,
  `risk-context.js`, `reviewer-dispatch.js`, `normalize.js`, `path-match.js`,
  `operation-contract.js` (`test/dependency-boundaries.test.js:36-45`).
- `index.js` may import only `github.js`, `operations.js`, `router.js`,
  `risk-context.js`, `reviewer-dispatch.js`, `normalize.js`, `path-match.js`
  (`test/dependency-boundaries.test.js:46-54`).

Neither list contains `protocol-v2.js`, `review-plan-authorization.js`,
`review-candidate-catalog.js`, or `routed-review-compiler.js`. There is
therefore **no legal import path from the Action entrypoint into any v2
module**, and the matrix is completeness-checked in both directions
(`test/dependency-boundaries.test.js:85-96`), so it cannot be bypassed by
adding a module and forgetting the matrix. Side-effect-only imports are caught
too (`test/dependency-boundaries.test.js:72-75`).

This is the single most actionable structural fact for this parent: the first
non-test change any adapter integration makes is an edit to that matrix, and
that edit is the moment the layering decision gets made — permanently, since
the matrix is the frozen record of it.

Two further matrix facts shape where the adapter layer can sit:

- `review-usage-reconciliation.js` and `review-deferred-recovery.js` are
  declared with `[]` allowed imports
  (`test/dependency-boundaries.test.js:30-31`) — they are leaves that duplicate
  rather than import the v2 vocabularies. Any adapter acknowledgment that must
  carry usage evidence into reconciliation crosses a boundary that does not
  currently exist as an import edge.
- `review-plan-authorization.js` may import `protocol-v2.js` and
  `review-budget-ledger.js` but **not** `review-candidate-catalog.js`
  (`test/dependency-boundaries.test.js:29`), while `routed-review-compiler.js`
  may import both (`:28`). So the compiler is the only module positioned to
  join catalog facts to plan facts — the adapter layer should consume compiled
  output, not re-join.

### 1.6 What genuinely does not exist

- **No preflight producer.** `decodeCandidatePreflight` has no counterpart that
  builds a preflight from a prepared request. Nothing counts tokens, proves
  pricing, or computes `maxExpectedCharge`.
- **No output-cap enforcement or finish-reason mapping.** `incomplete_token_limit`
  appears only as an enum member (`src/protocol-v2.js:136`) and a test fixture
  string (`test/protocol-v2.test.js:995`). Grep for `finish_reason` across
  `src/`, `test/`, `examples/`, `scripts/` returns only the *capability
  evidence* fields `finishReason` in `src/review-candidate-catalog.js:533`,
  `:779`, `:937` — i.e. the catalog can record that a candidate is *capable* of
  reporting a finish reason, but nothing ever reads one back.
- **No prepared-request fingerprint.** The v1 `requestFingerprint`
  (`src/operations.js:147`) is a *receipt* identity, not the PRD's
  prepared-request fingerprint that preflight and dispatch must share.
- **No actual-vs-configured model provenance.** The acknowledgment built at
  `src/operations.js:250-258` carries only `logicalDispatchId`, `backendId`,
  `status`, `acknowledgedAt`, `findingChannels`, and an optional `errorCode`.
  There is no actual model, no provider, no usage, no cost, no policy digest,
  no applied profile — so the PRD's "treat an actual-model mismatch as a policy
  violation" has nothing to compare against.
- **No prompt-profile resolution at the adapter boundary.** The PR-Agent job
  passes `CONFIG__MODEL` and nothing else profile-shaped
  (`examples/sd-review.yml:134`); PR-Agent's own defaults supply the prompt.
- **The outcome vocabulary is coarser than the PRD needs.** `ADAPTER_OUTCOMES`
  is `success | failure | cancelled | skipped` (`src/operations.js:21`), mapped
  to `adapter-failed | adapter-cancelled | adapter-skipped`
  (`src/operations.js:22-26`), and is fed directly from `needs.pr-agent.result`
  (`examples/sd-review.yml:178`). A GitHub job result cannot express
  `incomplete_token_limit` or "ambiguous side effect", so the acknowledgment
  channel itself must widen, not just the decoder.

## 2. Gaps vs PRD

Ordered by how much they block the children.

**G1 — No entrypoint path into the v2 layer (blocking, parent-owned).**
See §1.4. Until `test/dependency-boundaries.test.js` admits an edge, no child
can call `prepareManagedPlan`, `authorizePlan`, or any decoder. This is
squarely parent scope: it is the adapter *abstraction* decision.

**G2 — No preflight producer (blocking `integrate-pr-agent-review-adapter`).**
The PRD's second requirement and four of its acceptance criteria depend on a
side-effect-free preflight that does not exist. The *shape* is settled
(`src/protocol-v2.js:669-726`); the *producer* is not, and it needs a token
counter and a price source that the repository does not currently have.

**G3 — Acknowledgment channel too narrow (blocking both children).**
The PRD requires acknowledging configured/actual model, actual provider,
prompt-profile mode and applied identity, dispatch state, usage/cost reference,
policy digest, and bounded limitations. Today the channel is a GitHub job
result string (`examples/sd-review.yml:178`). Widening it is parent scope
because both children share it — and it is the one design decision that cannot
be made independently by either child.

**G4 — No durable-authorization gate on adapter side effects.**
`src/operations.js:414` gates on `result.dispatchAllowed` from the v1 receipt
store, not on a v2 child authorization. The PRD requires every side effect to
match a durable authorization *and* the exact preflight fingerprint.

**G5 — Output cap and finish reason unimplemented.** See §1.6.

**G6 — Prompt-profile identity never reaches the adapter.** See §1.6.

**G7 — Descriptor still v1 while manifest is v4.** No agreed carrier for v2
adapter configuration reaching a consumer repository (§1.5).

**Not a gap:** credential isolation (`examples/sd-review.yml:75-77`), empty
internal fallback (`examples/sd-review.yml:135` + `test/metadata.test.js:294`),
and single-target execution (preflight gate `examples/sd-review.yml:79-115`; one-container reviewer step `:116-159`) are already
delivered and test-covered. Three parent acceptance criteria can be closed by
citation rather than by new work — see §6.

## 4. Open Questions

1. **Where does the adapter layer live in the module graph?** Three shapes are
   viable and the choice is irreversible once the matrix is edited:
   (a) a new `src/review-adapter.js` importing `protocol-v2.js` +
   `routed-review-compiler.js`, with `operations.js` importing it;
   (b) `operations.js` importing v2 modules directly; (c) a second entrypoint
   (`src/index-v2.js`) with its own operation contract, leaving v1 untouched.
   (a) preserves the one-way layering the matrix exists to protect; (b) inverts
   it; (c) doubles the operation surface. Recommendation in §5.
2. **What widens the acknowledgment channel?** The job-result string
   (`examples/sd-review.yml:178`) cannot carry model/usage/finish-reason
   evidence. Options: the reviewer job writes a bounded JSON artifact that
   `acknowledge` reads; or a new `adapter-outcome-v2` JSON input decoded by a
   v2 decoder. The latter keeps the trust boundary in one decoder; the former
   survives a job that dies mid-run. Both children depend on this answer.
3. **Where do token counts and prices come from?** Preflight requires
   `countedInputTokens`, `maxExpectedCharge`, and price/unit evidence
   (`src/protocol-v2.js:676-696`). Nothing in the repository counts tokens or
   knows a price. Provider tokenizer endpoint, a vendored tokenizer, or a
   conservative character-ratio bound with `inputCounted: false`? The
   `inputCounted` flag exists precisely to make the conservative path honest,
   which suggests it was the intended answer — but no policy says so.
4. **Do v1 and v2 coexist, and for how long?** `.github/sd-github-review.json`
   pins `descriptor.path: config/routed-review-setup-v1.json` at
   `schemaVersion: 1`. If v2 adapters ship, does the v1 `adapter-request` path
   remain supported for un-migrated consumers?
5. **Is the park premise still the real blocker?** `task.json` notes record
   zero deployed consumers of `config/routed-review-setup-v1.json` across
   rwbp-coordinator, loadsmith, hoa-manager, and anomaly-metric-creator as of
   2026-08-15. That was not re-probed in this pass (read-only, no network). If
   it still holds, the reachability gap (§1.3) is the symptom and distribution
   is the disease — and this parent should stay behind distribution regardless
   of how well-specified it is.

## 5. Recommendations

**R1 — Make the matrix edit the first deliverable, and make it option (a).**
Introduce one new module (working name `src/review-adapter.js`) that imports
`protocol-v2.js` and `routed-review-compiler.js`, and add exactly one edge from
`operations.js` to it in `test/dependency-boundaries.test.js:36-45`. This keeps
`operations.js` ignorant of v2 vocabulary, preserves the one-way layering the
matrix was built to freeze (`test/dependency-boundaries.test.js:6-11`), and
gives both children a single named seam to target. Reject option (b): it puts
v2 decoders and v1 orchestration in the same module and the matrix will never
recover the distinction.

**R2 — Settle the acknowledgment channel before either child starts.** It is
the only parent-scope decision both children are blocked on (G3, Q2). Prefer a
new `adapter-outcome-v2` JSON input with a dedicated decoder, so the trust
boundary stays in one place, matching the existing pattern where
`decodeAdapterRequest`/`decodeAdapterAcknowledgment` are the sole validators
(`src/protocol.js:661`, `:728`). Extend `SEMANTIC_PAYLOAD_INPUTS`
(`src/operation-contract.js:245-252`) so a mis-wired step is rejected the same
way `acknowledge` already rejects foreign payloads.

**R3 — Close three acceptance criteria by citation, not by code.** Credential
isolation, empty internal fallback, and single-target invocation are already
delivered and tested (§2, "Not a gap"). Recording them as met shrinks the
parent to its genuine remainder and makes the residual scope honest.

**R4 — Choose the conservative token-counting path explicitly.** The
`inputCounted: false` branch already exists in the contract
(`src/protocol-v2.js:680`). Adopting a conservative bound with
`inputCounted: false` unblocks preflight without a tokenizer dependency, and
the PRD's "provider-compatible **or conservative** input tokens" language
(`prd.md:22-23`) already permits it. Write the decision down rather than
leaving it to the child.

**R5 — Do not start until the park premise is re-falsified.** Per `task.json`
notes, resume requires v1 actually distributed to fleet consumers *and* the
v2-governance scope deliberately revalidated. This research re-derived the
reachability half (9,390/13,136, §1.3) and it is unchanged. The distribution
half needs a live probe for `config/routed-review-setup-v1.json` across the
fleet — not performed here.

## 6. Cross-Child Integration Criteria

Contracts the parent must fix so the two children can be built independently
and still compose. Each is testable at the parent level.

**C1 — One authorization gate, one call site.** Both children consume the same
`authorizePlan` result (`src/review-plan-authorization.js:928`) and neither
re-derives authorization. Test: the durable-authorization check appears in
exactly one module — mirror the existing single-definition assertion pattern at
`test/dependency-boundaries.test.js:130-146`, which already proves
`selectProtocolRoute` is defined only in `router.js`.

**C2 — One acknowledgment shape, two producers.** Copilot emits
`promptProfile.mode: "handler-managed"`; PR-Agent emits `"referenced"` with
alias/version/digest. Both use the same decoder
(`src/protocol-v2.js:494` for the binding). Test: a Copilot acknowledgment
carrying a referenced profile is rejected, and a PR-Agent acknowledgment
lacking an applied digest is rejected.

**C3 — Disjoint credentials, asserted structurally.** Extend the existing
permission-union machinery (`src/operation-contract.js:262-272`) so the reviewer
operation's permission map and the finalizer's are proven disjoint on `checks`.
The workflow already satisfies this (`examples/sd-review.yml:75-77` vs
`:165-169`); the contract does not yet *state* it, so a future edit could
silently break it.

**C4 — Shared reconciliation vocabulary.** Both children route uncertainty into
the same terminal state. The v1 precedent is `src/operations.js:440-450`. Test:
for each of timeout, ambiguity, changed head, and replay, both children produce
`reconciliation-required` and neither advances to another candidate.

**C5 — Lane preservation across handler kind.** The logical cheap/deep lane
must survive selection of either handler (parent AC 1, and copilot child AC 3).
Test: a `cheap` lane request routed to native Copilot and the same request
routed to PR-Agent both report `selectedRoute: "cheap"`.

**C6 — No child-to-child import.** Neither adapter module may import the other;
both import only the shared seam from R1. Test: the matrix
(`test/dependency-boundaries.test.js:18-55`) lists no edge between them, and
the completeness check at `:85-96` forces the matrix to be updated when either
module is added.
