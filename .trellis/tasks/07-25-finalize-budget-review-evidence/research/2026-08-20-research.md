## Gaps vs PRD

1. **No v2 budget-review receipt exists.** This is the single largest gap.
   PRD `prd.md:19-23` requires a bounded exact-head receipt carrying lane,
   chain, candidate, handler, prompt-profile identity/mode, configured token
   limits, counted/reported usage, finish reason, reservation, actual cost,
   variance, hard request limit, pool state, policy outcome, deferral, and
   recovery links. `src/protocol-v2.js` has `decodeLocalReviewReceipt`
   (`:1258`) for the local-attested lane only, and `src/receipt.js` implements
   the v1 routing receipt. Nothing decodes or builds the budget receipt.

2. **No acknowledgment-vs-authorization provenance validator.**
   PRD `prd.md:10-13` requires validating configured/actual model, prompt-profile
   mode and applied alias/version/digest, provider, exact head, and outcome
   against durable authorization. The v1 acknowledgment decoder
   (`src/protocol.js:729-762`) validates only `status`, `errorCode`,
   `logicalDispatchId`, `backendId`, `acknowledgedAt`, `findingChannels` — no
   model comparison, no profile comparison, no head binding.
   `decodePromptProfileBinding` (`src/protocol-v2.js:494`) exists but nothing
   cross-checks an acknowledgment against a binding.

3. **Nothing publishes the two Checks.** The names, conclusions, projection
   schema, and CAS rule all exist; the publisher does not. No call to
   `createCheckRun` uses `ASSURANCE_CHECK_NAME` or `GATE_CHECK_NAME`, and no
   function maps `decodeReviewOutcomes` output to a conclusion/title/summary.
   The mandated deferred-pass title `Merge allowed; review assurance deferred`
   (`prd.md:70`, `design.md:31`) appears **nowhere** in `src/` or `test/`.

4. **No status / pending / explain / recovery / discovery responses.**
   `decodeSetupDiscoveryV2` decodes a discovery document, but no operation
   emits one — `src/operation-contract.js:28-131` declares no such operation,
   and `DURABLE_OUTPUTS()` (`:137-171`) has no field for one.

5. **No branch-protection diagnostic is possible today.** `prd.md:38-39`
   requires identifying a missing required gate or an incorrectly required
   assurance Check. `GitHubClient` has no branch-protection or ruleset read
   method (`src/github.js` exposes only the three Check methods above), so the
   diagnostic has no data source.

6. **No `budgetOutcome` field on any schema.** `NOT_MANAGED_BUDGET_OUTCOME`
   exists (`src/protocol-v2.js:34`) but `decodeReviewOutcomes` (`:806`) returns
   only three axes — review, assurance, gate. `prd.md:42-45` requires
   standalone evidence to carry `budgetOutcome=not_managed`, which has no
   carrier.

## Staleness in existing design/implement

**Neither `design.md` nor `implement.md` contains a single file path or
`file:line` citation.** They are pure contract prose. So there are no stale
citations to repair. What follows are the substantive drifts.

### Verdict: `design.md` — sound in intent, two vocabulary drifts

The boundary statement (`design.md:4-9`), the three-axis separation
(`design.md:20-25`), the Check semantics (`design.md:27-32`), and the rollback/
CAS rules (`design.md:52-59`) all match what `decodeReviewOutcomes`
(`src/protocol-v2.js:806-875`) and `authorizeProjectionWrite`
(`src/protocol-v2.js:1351-1381`) actually enforce. The design is not stale in
intent and I left the prose unchanged.

Two drifts, both naming, both real:

- `design.md:23` (and `prd.md:28`) says record `reviewOutcome=deferred_budget`.
  `REVIEW_OUTCOME_STATES` (`src/protocol-v2.js:109-116`) has no such state.
  The shipped encoding is `reviewOutcome.state = "skipped"` with
  `reasonCode = "budget_exhausted_deferred"` (`src/protocol-v2.js:141`), which
  `decodeReviewOutcomes` special-cases at `:838-839`.
- **Two gate vocabularies coexist in-tree.**
  `GATE_OUTCOME_STATES = ["pass","block"]` (`src/protocol-v2.js:127`) versus
  `RECOVERY_GATE_OUTCOMES = ["blocked","passed"]`
  (`src/review-deferred-recovery.js:78`), with `gateOutcome()`
  (`src/review-deferred-recovery.js:513-516`) returning the *past-tense* form.
  The lane merge policy is spelled `["block","allow"]` in both
  (`src/protocol-v2.js:74`, `src/review-deferred-recovery.js:74`), which is
  consistent. Finalization sits exactly on the seam between these two modules
  and must reconcile them; `design.md:24-25` picks the `pass|block` spelling
  without acknowledging the other exists.

### Verdict: `implement.md` — sound as a sequence, one missing input and one oversized step

Steps 1-7 (`implement.md:3-16`) still describe work that genuinely does not
exist. Nothing in the plan is already done, so nothing is stale in that sense.
Two issues:

- **Step 6** ("branch-protection readiness diagnostics") has no data source.
  It needs a new `GitHubClient` read method that does not exist today
  (`src/github.js` has no branch-protection call), and the enclosing operation
  would need a new permission beyond the `checks: read|write` currently
  declared (`src/operation-contract.js:116`, `:130`). The plan does not name
  either prerequisite.
- **Step 4** bundles status, pending, explain, recovery, discovery,
  retention-status, and purge projections into one step. These span at least
  three modules (`protocol-v2.js`, `review-deferred-recovery.js`,
  `retention-policy.js`) totalling ~4,550 lines of existing contract. That is
  not one implementation step.

## Open Questions

1. **Is the park's distribution premise actually resolved?** The park resumed
   "only when v1 is actually distributed to fleet consumers AND the v2-governance
   scope is deliberately revalidated." `task.json` records the 2026-08-20 unpark
   as an owner directive (`unpark-all`) with no statement that distribution
   changed. Falsifying this needs a read of the four named fleet repos for
   `config/routed-review-setup-v1.json` — outside this repo, not done here.
2. **What happens to `sd-github-review/receipt`?** `design.md:57-59` says setup
   diagnostics verify only the gate Check is required "before the old
   branch-protection Check is retired," but never names it. Do assurance and
   gate ship *alongside* `sd-github-review/receipt` (`src/receipt.js:11`), or
   does gate replace it? Consumers that pinned branch protection to the receipt
   Check break either way without a migration story.
3. **Does `08-09-review-gate-advisory-convergence` supersede part of this?**
   That task (still `planning`) is about the live local review gate blocking on
   any finding. It touches the same gate concept from the shipped side.
4. **Which gate vocabulary wins** — `pass|block` or `passed|blocked`? Changing
   `review-deferred-recovery.js` breaks a 28.5 KB green test file; changing
   `protocol-v2.js` breaks a 42 KB one. Cheapest is a translation at the
   finalization boundary, which is where this task lives.
5. **Where does the budget receipt physically live** — a new Check output, a new
   marker on an existing Check, or private storage? `prd.md:19-23` says
   "publish" without naming a carrier, and the 32 KiB Check-text ceiling
   (`src/receipt.js:14`) constrains the answer.

## Recommendations

1. **Fix the vocabulary in `prd.md`/`design.md`, not in the code.** The
   `deferred_budget` naming and the `pass|block` spelling are planning-document
   inventions; the code is shipped-green and tested. Rewrite `prd.md:28` and
   `design.md:23` to the `skipped` + `budget_exhausted_deferred` encoding that
   `decodeReviewOutcomes` already enforces, and state explicitly that the
   finalization layer translates `review-deferred-recovery.js`'s past-tense
   gate outcomes. I did **not** make this edit — it changes a stated contract
   and needs owner sign-off.
2. **Split this task.** Its natural core is the acknowledgment validator, the
   budget receipt, and the two-Check publisher (implement.md steps 1-3, 6-7).
   Step 4's status/pending/explain/discovery/retention/purge projections and
   step 5's retention metadata belong in a separate child. As written, one task
   spans four modules and every acceptance criterion in `prd.md:56-84`.
3. **Resolve the distribution premise before `task.py start`.** If zero fleet
   consumers still read `config/routed-review-setup-v1.json`, this task adds
   ~1,000 more unreachable lines to the 9,390 already there.
4. **Decide the receipt Check migration story** (open question 2) as a
   prerequisite, not as a step-6 detail.
5. **Consider adding a reachability assertion** to
   `test/dependency-boundaries.test.js`, which today only checks import
   direction (`:98-108`). A test that fails when a module is unreachable from
   `src/index.js` would have surfaced the 71% drift as it accumulated.
