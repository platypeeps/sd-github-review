## Current State

### The native Copilot lane that exists today

There are two entrypoints and one shared dispatch service.

- **Shared service.** `requestCopilotReviewer` (`src/reviewer-dispatch.js:9-44`)
  runs a presence probe — requested-reviewer set, then head-commit reviews with a
  case-insensitive `commit_id` match skipping `DISMISSED`
  (`src/reviewer-dispatch.js:16-27`) — and issues `requestReviewer` only when
  neither shows Copilot present (`:40-42`). It returns
  `{alreadyRequested, alreadyReviewed, alreadyPresent, requested, rerequested}`.
- **Standalone entrypoint.** `src/index.js:265-272` requests Copilot when
  `decision.route === "copilot"` and `request-copilot` is true. No receipt, no
  observation, no rerequest — `forceRerequest` is not passed.
- **Durable entrypoint.** `src/operations.js:416-441` is the whole native adapter:
  it calls `requestCopilotReviewer` with
  `forceRerequest: Boolean(request.rerequestOf) && rerequest-authorized`
  (`:423-425`), then immediately calls `store.observe(...)` with
  `alreadyPresent: !dispatch.requested` (`:427-437`) in the same job step.
  Any throw becomes a `reconciliation-required` result (`:440-450`).

### Backend and lane separation

`selectedBackend` (`src/operations.js:131-137`) maps `copilot` to the fixed
`copilotBackend` record (`:110-128`: `id: "github-copilot"`, `kind: "copilot"`,
`supportsRerequest: true`, `reviewAuthors: [reviewer]`) and requires
`kind === "external"` for `cheap`/`deep`. `src/protocol.js:867-869` enforces the
same invariant on the receipt (`receipt.backend.kind must be copilot for the
copilot route`), and `:871-873` the mirror for cheap/deep. The logical
cheap/deep lane is therefore already structurally separate from the native
Copilot handler.

### Receipt, identity, and idempotency

`ReceiptStore.begin` (`src/receipt.js:487-...`) creates one receipt keyed by
`logicalDispatchId`, with `dispatch.idempotencyKey = request.logicalDispatchId`
(`src/receipt.js:453,459`) and `attempt` carried on the receipt
(`src/receipt.js:471`). `src/protocol.js:551-553` requires
`attempt === rerequestOf.priorAttempt + 1`, so a distinct authorized attempt is
a distinct logical identity and a replay of the same attempt collapses onto the
existing receipt.

`ReceiptStore.observe` (`src/receipt.js:661-703`) writes
`status: alreadyPresent ? "already-present" : "requested"` at
`src/receipt.js:694` and moves `phase` to `observed`. It re-asserts the live head
before mutating (`src/receipt.js:396-399` in `#updateRecord`), so a head change
mid-flight becomes `reconciliation-required` rather than a silent write.

### What PR #93 (`08-16-bind-copilot-review-evidence`) delivered

**No code landed in this repository.** That task's own design says so
explicitly: `scripts/` no longer carries the pack executables since the thin
conversion, so the fix landed upstream in `platypeeps/sd-ai-command-pack`
(archived `design.md:102-125`). What landed here on PR #93 was the spec record

What it changed, in substance:

- Upstream, from pack **0.71.24**, the coordinator now *consumes* the
  `dispatch.status` discriminator the Action was already writing. Every terminal
  report produced after remote observation carries the
  `remote-evidence-not-dispatch-caused` limitation when the receipt says
  `already-present`.
- Here, `.trellis/spec/backend/consumer-installer.md:580-635` ("What a Copilot
  receipt does and does not prove") records the proves / does-not-prove /
  closes-the-gap split and the receipt-to-reading table.

**Why this matters to the present task.** Before #93, `requested` versus
`already-present` was a field nobody read; the Copilot request and the evidence
harvested from it were only loosely coupled. After #93 the discriminator is
load-bearing downstream. Anything this task does to the request path — a bounded
observation window, an acknowledgment shape, a new reconciliation state — now has
a consumer that will read it, and must not break that reading.

**What #93 did *not* deliver:** none of the five steps in this task's
`implement.md`. No fixtures were added, no authorization gate, no bounded
observation window, no acknowledgment emission, no permissions/replay/rollback
documentation for the native adapter.

## Open Questions

1. **Does this task still want the v2 scope?** The park was lifted by owner
   directive (`unpark-all`), not because either premise was falsified. I
   re-derived reachability today and it is *unchanged* at 9,390/13,136. The park
   note's second premise (zero deployed fleet consumers) was not re-probed here —
   that needs a live check against `rwbp-coordinator`, `loadsmith`,
   `hoa-manager`, `anomaly-metric-creator` for `config/routed-review-setup-v1.json`.
   **I could not verify that from this repository.**
2. **What does "bounded window" mean for a synchronous lane?** The Copilot review
   arrives minutes after the request; the Action's `route` step returns in
   seconds. Delivering a real observation window means either a second job
   (a `poll`/`observe` operation) or a scheduled re-entry. Which one is intended
   is not recorded anywhere.
3. **Is an acknowledgment for the Copilot lane wanted at all?** The `acknowledge`
   operation was deliberately shaped around external adapters
   (`src/operation-contract.js:93-101`, `needsClient: "no"`, `permissions: {}`).
   Extending it to Copilot means either widening that contract or adding a
   native-specific operation.
4. **Does #93's `already-present` steady state undercut requirement 2?** In this
   repository the ruleset almost always wins the race, so the Action's request is
   usually a no-op. A "bounded request identity" for a request that never fires
   is thin. Worth deciding whether the ruleset overlap (`consumer-installer.md:520-534`)
   should be revisited before building more on top of the request path.
5. **PRD acceptance criterion 1 is already met.** The A-001 clause was reassigned
   to `08-04-harden-copilot-rerequest-dispatch` in the ledger but never removed
   from this PRD. Should it be struck, or retained as a regression guard?

## Recommendations

1. **Split the task at the v1/v2 seam before starting.** Three PRD requirements
   (candidate-bound authorization, bounded window, acknowledgment shape) require
   v2 reachability; two (idempotent request, reconciliation states) are v1 and are
   largely already done. Planning them as one unit is what produced a task that
   looks 60% delivered and 40% architecturally blocked.
2. **Strike or downgrade the A-001 requirement and acceptance criterion.** They
   are closed, owned elsewhere, and covered by two named regression tests. Keeping
   them as an open acceptance criterion overstates the remaining work.
3. **If the v1 slice ships first**, the highest-value undone items are the ones
   with no v2 dependency: (a) a secret-boundary test for the Copilot lane
   asserting the `review` job's inputs and outputs carry no `*__KEY`, closing the
   one acceptance criterion with zero coverage — model it on the PR-Agent-side
   assertion at `test/metadata.test.js:281-289`, and note it will need
   `examples/sd-review.yml` added to the workflow list at
   `test/metadata.test.js:170-174`, which is the same one-line change the
   PR-Agent sibling's Step 1 already owns, so coordinate rather than duplicate;
   (b) an explicit unmatched/late
   completion reconciliation state; (c) replay and rollback documentation
   rewritten against installer-managed route mode.
4. **Do not build a timestamp guard.** #93 established that
   `submitted_at >= dispatch.startedAt` cannot discriminate here — the ruleset
   requests early and Copilot submits late (`consumer-installer.md:600-606`).
   Any observation-window design must key off `dispatch.status`, not time.
5. **Whatever ships must preserve the `requested` / `already-present`
   discriminator exactly.** It is now consumed upstream from pack 0.71.24
   (`consumer-installer.md:608-616`) and is the only thing making Copilot evidence
   attribution honest. Changing when `alreadyPresent` is computed silently changes
   what every downstream report claims.
