2. **No v2 attempt receipt.** Grep for `attemptReceipt`, `decodeAttemptReceipt`,
   `receiptV2` across `src/*.js` returns nothing. `src/receipt.js` is the v1

   provider+model / budget state / usage / deferral) has no home yet. The orphan task
   `08-04-define-v2-receipt-and-identity-contracts` (parent `None`) appears to be
   exactly this scope.

3. **No status / pending / explain / recovery consumer contracts.** Grep for
   `decodeStatus`, `decodePending`, `decodeExplain` across `src/*.js` returns nothing.
   Only setup discovery (`src/protocol-v2.js:1383`) of the five bounded consumer

   `decodeLocalAttestationRequest` (`src/protocol-v2.js:1182`) and
   `decodeLocalReviewAuthorization` (`:1211`) are referenced only from
   `test/protocol-v2.test.js:493`. No authenticated ingestion path and no

## Open Questions

1. **Was the second park premise re-checked?** The park resumes only when v1 is actually
   distributed to fleet consumers AND the v2 scope is deliberately revalidated. This
   pass re-verified reachability exactly (9,390/13,136, unchanged) but did **not** probe
   `rwbp-coordinator`, `loadsmith`, `hoa-manager`, or `anomaly-metric-creator` for
   `config/routed-review-setup-v1.json` — that needs network access. The 2026-08-15
   check found all four 404. If they still 404, the `unpark-all` directive overrode a
   park whose premises both still hold, which is a scope decision the owner should
   confirm rather than something research can settle.

2. **Where does the v2 receipt contract live?** `08-04-define-v2-receipt-and-identity-contracts`
   has `parent: null` but is squarely inside this task's stated ownership ("Own the
   schemas, ... receipts, checks, and setup-discovery contracts"). Should it be
   re-parented under this task or under `07-25-finalize-budget-review-evidence`?

3. **Does the v1 descriptor advance to v2, or ship alongside?** The PRD requires
   rejecting v1 selectors for new dispatch while keeping historical v1 receipts
   readable. Whether that means a new `contract/routed-review-setup-v2.json` published
   next to the v1 file, or an in-place `contractMajor` bump with
   `supportedContractMajors: [1, 2]`, is not decided in either artifact and drives the
   installer's manifest schema (currently 4).

4. **Is `07-25-finalize-budget-review-evidence` decomposable?** It carries gaps 1, 2,
   and 3 above — receipts, both check projections, and four consumer contracts — with no
   children, while its two sibling children each have their own decomposition. It is
   plausibly the largest single remaining unit in the tree.

## Recommendations

1. **Settle the park question before any code.** Re-probe the four fleet consumers for
   `config/routed-review-setup-v1.json`. If they still 404, take an explicit owner
   decision to proceed anyway and record it in `task.json` notes, rather than letting
   `unpark-all` stand as the rationale. This is cheap and it is the one thing that
   determines whether the rest of the work is worth doing now.

2. **Sequence the remaining children as evidence → standalone → local-attested.**
   `07-25-finalize-budget-review-evidence` unblocks the most acceptance criteria
   (receipts, both check projections, status/recovery/discovery) and both siblings
   depend on being able to *project* an outcome. Decompose it first (see Open
   Question 4).

3. **Make un-quarantining a gate, not a cleanup step.** Each child that wires a module
   into the entrypoint should, in the same change, remove it from
   `scripts/check-coverage.mjs:39-46` and add it to `package.json`'s `check` script,
   with the per-file coverage floor set alongside the existing
   `src/index.js` floor (`scripts/check-coverage.mjs:52`). Doing this incrementally
   avoids one 9,390-line coverage cliff at the end.

4. **Add a reachability assertion to `test/dependency-boundaries.test.js`.** It already
   encodes the v2 layering at `:24-29`; an explicit test that walks imports from
   `src/index.js` and asserts the reachable set equals the `npm run check` set would
   make the quarantine's shrinkage visible and prevent a module from being wired in
   while staying unmeasured.

5. **Pick the descriptor strategy early (Open Question 3).** It is upstream of setup
   discovery, the installer manifest, and the v1→v2 migration story, and all three of
   the remaining children touch it.

6. **Do not treat the existing green suite as coverage of this work.** 647 passing tests
   exercise the v2 modules as isolated pure functions. None of them prove an
   end-to-end compile → authorize → dispatch → receipt → check path, which is what
   every acceptance criterion in the PRD is actually written against.
