# Research: bound cheap review token usage (2026-08-20)

Scope: where the cheap PR-Agent lane is configured and invoked, what token/cost
controls exist today, and how much of this task's PRD is already satisfied by
code that landed after the July planning artifacts were written.

Method note: every repository claim below is a `file:line` citation read at
commit `40df292`. Upstream PR-Agent claims were read from the tagged source at
`v0.39.0` (both `qodo-ai/pr-agent` and the `The-PR-Agent/pr-agent` fork the docs
link to), not from the pinned image bytes — see Open Questions.

## Current State

### The cheap lane has no token or cost control anywhere on the live path

`src/index.js` is the Action entrypoint. For the cheap route it emits exactly one
piece of provider configuration — the model id — and nothing else:

- `src/index.js:275-280` picks `cheap-model` or `deep-model` and calls it `model`.
- `src/index.js:124` sets `run-external-reviewer` true for `cheap` and `deep`.
- `action.yml:102-103` describes `cheap-model` as "Provider model identifier
  emitted when the cheap route is selected". `action.yml` declares no token,
  budget, or cost input at all.

The actual reviewer invocation lives in the workflow templates, not in `src/`.
All three PR-Agent templates run the pinned container directly and pass three
`CONFIG__*` variables:

- `examples/pr-agent-router.yml:114-116` (`CONFIG__MODEL`,
  `CONFIG__FALLBACK_MODELS`, `CONFIG__RESTRICTED_MODE`), invoked at
  `examples/pr-agent-router.yml:119-139`.
- `examples/sd-review.yml:134-136`, invoked at `examples/sd-review.yml:139-157`.
- `examples/pr-agent-on-demand-review-router.yml:129-131`, invoked at
  `:134-152`.

None of the three sets an input cap, an output cap, a per-request cost limit, or
any `.pr_agent.toml`. The container is pinned by digest
`pragent/pr-agent@sha256:cae31b51…` in all three (`examples/pr-agent-router.yml:137`).

`examples/pr-agent-router.yml` is the installer-managed workflow
(`scripts/consumer-installer/codecs.mjs:10`, `:38-44`) and `examples/sd-review.yml`
is the installer-managed durable lane (`codecs.mjs:16-17`, `:51-56`), so a change
to either is a fleet-visible change, not a docs edit.

### Route mode is installer-managed at manifest schema 4

Confirmed and current:

- `MANIFEST_SCHEMA_VERSION = 4` at `scripts/consumer-installer/codecs.mjs:159`;
  supported set `{1,2,3,4}` at `:160`.
- `REVIEW_ROUTE_MODE` joined the managed-variable table at schema 4
  (`codecs.mjs:131-139`), gated by `ROUTE_MODE_MIN_SCHEMA_VERSION = 4`
  (`codecs.mjs:171`) and version-scoped decoding via `configVariablesForSchema`
  (`codecs.mjs:176-180`).
- The installed lane fails closed on an unset `REVIEW_ROUTE_MODE`
  (`examples/pr-agent-router.yml:25-41`), and `codecs.mjs:116-123` documents that
  `ROUTE_MODES` and the lane's `case` statement are asserted equal by a test
  (`test/consumer-installer.test.js:1973`).

This is the precedent shape for any new managed spend control: a repository
variable would need a manifest schema bump and the same version-scoped decode
tier, not a new field bolted onto schema 4.

## Gaps vs PRD

Ordered by how much they change the plan.

### G1. PR-Agent v0.39.0 cannot accept a general output-token cap (blocking)

The PRD requires "Send the configured hard output-token cap to the provider" and
the design's rollback gate requires proving the cap before enabling a candidate.
In `pr_agent/algo/ai_handlers/litellm_ai_handler.py` at v0.39.0, `max_tokens` is
passed to `litellm.acompletion` in exactly one case — Claude extended thinking,
via `extended_thinking_max_output_tokens` (default 4096), gated on
`enable_claude_extended_thinking`. There is no general output-cap setting.

For the configured OpenRouter cheap model this means the output cap is not
expressible through the pinned container's configuration surface at all. Per the
design's own fail-closed rule, that is a "do not enable" condition, not a
"configure it" task.

### G2. PR-Agent's only input control is the silent truncation the PRD forbids

The PRD forbids truncating, summarizing, segmenting, or sampling source. PR-Agent's
input bound works by exactly that:

- `get_max_tokens(model)` (`pr_agent/algo/utils.py`) takes the model's entry from
  `MAX_TOKENS`, or `config.custom_model_max_tokens` if positive, then further
  reduces it by `config.max_model_tokens` when set.
- `pr_agent/algo/pr_processing.py` uses that value as a pruning threshold:
  `get_pr_multi_diffs` clips via `clip_tokens(patch, delta_tokens, …)` when the
  policy is `clip`, and `generate_full_patch` skips whole files against
  `OUTPUT_BUFFER_TOKENS_SOFT_THRESHOLD` / `…_HARD_THRESHOLD`.

`max_model_tokens` defaults to `32000` in `pr_agent/settings/configuration.toml`.
So the cheap lane today already has an implicit ~32k input ceiling enforced by
clipping and file-skipping — an unenforced, undocumented, PRD-violating bound
that is live in the fleet right now. Setting `CONFIG__MAX_MODEL_TOKENS` would
tighten that bound, not satisfy the PRD; it would make the prohibited behavior
more aggressive.

### G3. The configured default models are absent from PR-Agent's MAX_TOKENS map

`scripts/consumer-installer/codecs.mjs:66-70` defaults to
`openrouter/qwen/qwen3-coder-30b-a3b-instruct` (cheap) and
`openrouter/moonshotai/kimi-k2.6` (deep). Neither string appears in
`pr_agent/algo/__init__.py`'s `MAX_TOKENS` at v0.39.0 (the only near matches are
`groq/qwen/qwen3-32b` and `groq/moonshotai/kimi-k2-instruct`). `custom_model_max_tokens`
defaults to `-1`, and no template sets `CONFIG__CUSTOM_MODEL_MAX_TOKENS`.

By the `get_max_tokens` logic quoted above, that path raises:
`Ensure {model} is defined in MAX_TOKENS … or set a positive value for it in
config.custom_model_max_tokens`.

`SETUP-PR-AGENT.md:250-253` acknowledges the hazard in the abstract ("Some models
also require `custom_model_max_tokens` … the workflow does not guess that value")
but the shipped defaults are among the models that require it. This reads as a
live defect in the default configuration, independent of this task's budget work,
and it should be confirmed against a real run before being treated as one (see
Open Questions).

### G4. `hardInputLimit` is never compared to counted input at preflight

This is the one genuine code gap inside the v2 layer. The catalog carries
`hardInputLimit` (`src/review-candidate-catalog.js:497-500`, `:924`) and
reconciliation compares actual usage against it
(`src/review-usage-reconciliation.js:709-714`), but the pre-dispatch classifier
never does. `classifyEligibility` (`src/review-plan-authorization.js:494-506`)
checks head, capability, `inputCounted`, pricing, enforceability, unit match, and
`conservativeMaxCharge` against cost limits — it never compares
`preflight.countedInputTokens` to `hardInputLimit`, and there is no
`input_token_limit` reason in `PREFLIGHT_INELIGIBILITY_REASONS`
(`:80-88`). Symmetrically, nothing asserts `preflight.outputCap <= hardOutputLimit`.

So the PRD's central pre-dispatch requirement is the part that is *not* built,
while the surrounding machinery is.

### G5. Finish-reason evidence does not cross the container boundary

`incomplete_token_limit` exists as a reason code (`src/protocol-v2.js:136`) and
PR-Agent does capture `finish_reason` internally (`litellm_ai_handler.py` returns
`resp, finish_reason, response_obj` and logs it). But the templates invoke
PR-Agent as a bare `docker run` (`examples/pr-agent-router.yml:119-139`) whose
only machine-readable result is an exit status. There is no adapter process to
read a finish reason, no usage payload, and no acknowledgment path back into the
receipt runtime for the cheap lane. This is precisely what
`07-25-integrate-pr-agent-review-adapter` owns, and it is still in `planning`.

### G6. Naming drift between PRD and code

The PRD says `ineligible_pre_dispatch` with reason `input_token_limit`. The code
uses outcome `input_ineligible` (`src/protocol-v2.js:135`) with reasons from
`PREFLIGHT_INELIGIBILITY_REASONS`. Implementation should adopt the existing
names and add `input_token_limit` to that frozen set rather than introduce a
parallel vocabulary. Not corrected in `prd.md` — flagging only, since the PRD is
the owner's requirements document.

## Staleness in the existing design/implement artifacts

Both artifacts predate the v2 governance modules and the installer's schema-4
route-mode work. Neither contains a `file:line` citation, so nothing is literally
mis-cited; the staleness is in their assumptions.

**`design.md`** — intent holds and its three-boundary table matches the shipped
vocabulary almost exactly (`within_reserve`/`budget_overrun`/`policy_violation`,
`overdrawn`, quarantine, no post-dispatch fallback). Two assumptions are stale:

1. "the adapter applies the compiled safe projection where the runtime supports
   that contract" presumes an adapter exists. There is none for the cheap lane;
   PR-Agent runs as a bare `docker run` and the compiled-projection path
   (`routed-review-compiler.js`) is unreachable from `src/index.js`.
2. The rollback gate is written as a policy choice, but G1 and G2 turn it into
   the *current verdict* for the pinned runtime: the output cap is unexpressible
   and the input bound is truncation-based.

Updated in place: added a "Runtime Capability Verdict" section recording the
verified PR-Agent v0.39.0 facts and the resulting fail-closed conclusion, and
qualified the adapter sentence. Everything else left as written.

**`implement.md`** — materially stale. Steps 2, 3, 4 and 6 describe work that has
since landed:

- Step 2 ("Extend catalog, compiled-policy, authorization, acknowledgment,
  receipt, and reconciliation fixtures with hard input/output/cost limits and
  explicit units") — done: `review-candidate-catalog.js:497-535`,
  `review-usage-reconciliation.js:497-511`, plus
  `fixtures/protocol/v2/candidate-safe-projection.*.json`.
- Step 4 (conservative maximum request cost, reserve) — done:
  `protocol-v2.js:685-697`, `review-budget-ledger.js:755-864`.
- Step 6 (soft/hard classification, quarantine, overdrawn) — done:
  `review-usage-reconciliation.js:684-745`, `:800-803`, `:875-880`.
- Step 3 is half-done: counting and rejection scaffolding exists, but the
  `hardInputLimit` comparison at preflight (G4) does not.
- Step 1 is the step that should now run first and gate the rest, and its answer
  is largely already in hand (G1–G3).

Its Validation block is also wrong on one concrete point: `npm run check`
(`package.json:12`) syntax-checks only the 11 reachable `src/` files plus the
installer scripts. It does not cover `protocol-v2.js`,
`review-plan-authorization.js`, `review-candidate-catalog.js`,
`review-budget-ledger.js`, or `review-usage-reconciliation.js` — the exact files
this task would edit. `npm test` (`node --test`) does cover their test files.

Rewritten in place to reflect what is built, what remains, and the capability
gate that now precedes everything.

## Open Questions

1. **Does the pinned digest actually correspond to v0.39.0 source?** The repo
   asserts it (`SETUP-PR-AGENT.md:18-19`) and I read the v0.39.0 tag, but I did
   not pull `pragent/pr-agent@sha256:cae31b51…` and diff its `pr_agent/` tree.
   G1–G3 rest on that correspondence. A `docker run --rm --entrypoint cat <digest>
   /app/pr_agent/algo/__init__.py` would settle it.
2. **Is G3 actually firing in production?** `08-15-prove-routed-lane` is archived,
   which suggests the lane ran successfully at some point. Either the pilot used a
   model that *is* in `MAX_TOKENS`, or LiteLLM normalizes the model string before
   `get_max_tokens` sees it, or the failure is real and unobserved because no
   consumer has the lane enabled (`task.json` notes: all four probed consumers
   404 on the descriptor). Worth one deliberate run before filing it as a defect.
3. **Is a PR-Agent-shaped adapter the right vehicle at all?** Every enforcement
   requirement in the PRD needs a process that prepares the request, counts it,
   caps output, and reads back finish reason plus usage. PR-Agent v0.39.0 exposes
   none of those to its caller. A direct LiteLLM/provider call under this repo's
   own control would satisfy the PRD; PR-Agent as currently pinned cannot.
4. **Where would an enforced limit be configured?** If limits become
   fleet-visible (repository variables), that is a manifest schema 5 with a new
   version-scoped decode tier (`codecs.mjs:159-180` is the pattern). If they live
   only in the pinned private catalog, no installer change is needed but the
   catalog has no consumer on the reachable path.
5. **Do measured routine PR payloads exist?** The PRD requires budgets "based on
   measured routine PR payloads". No measurement data was found in the repo.

## Recommendations

1. **Resolve Step 1 first and treat it as a gate, not a task.** The capability
   qualification is now mostly answered and the answer is negative for the pinned
   runtime. Confirm Open Question 1 by inspecting the pinned image, then record
   the verdict. If it holds, this task cannot deliver its acceptance criteria
   against PR-Agent v0.39.0 as invoked today, and that is the finding to
   surface — not a reason to weaken the criteria.
2. **Split the work along the reachability line.** G4 (`hardInputLimit` at
   preflight, `input_token_limit` reason, `outputCap <= hardOutputLimit`) is
   self-contained, testable, and lands in code that already has a test suite. It
   is worth doing regardless of the runtime verdict, and it closes the one real
   modeling gap. The rest of the PRD depends on an adapter that does not exist.
3. **Do not sequence this ahead of `07-25-integrate-pr-agent-review-adapter`.**
   Five of the ten acceptance criteria (output cap reaching the model,
   finish-reason distinction, reservation against a real request, reconciliation
   of real usage, bounded usage metadata) require the adapter's evidence path.
   Without it they can only be satisfied against fixtures, which would produce
   green tests over a lane that enforces nothing.
4. **File G3 separately.** A default cheap model that raises in `get_max_tokens`
   is a shipped-configuration defect with a much smaller blast radius than this
   task, and it should not wait behind a governance wave.
5. **Document the current implicit bound now.** `SETUP-PR-AGENT.md` should state
   that the pinned container silently clips patches at a default 32k
   `max_model_tokens` and skips files past its output buffer thresholds. That is
   the PRD's own last acceptance criterion ("Documentation distinguishes
   context-window capacity from enforced token and spend budgets"), it is
   independently true today, and it is cheap.
6. **Budget the installer cost before touching a template.** Editing
   `examples/pr-agent-router.yml` changes its SHA-256, which is the manifest's
   `source.sha256` (`codecs.mjs:326-338`) and the adopt-path recognition key. The
   comment at `codecs.mjs:186-204` requires adding the superseded release hash to
   `HISTORICAL_TEMPLATE_HASHES` so existing manual installs stay adoptable. Note
   also that `examples/sd-review.yml` — an installer-managed resource — is not
   covered by the pinned-workflow assertion in `test/metadata.test.js:161-175`,
   which checks only `pr-agent-router.yml` and
   `pr-agent-on-demand-review-router.yml`.
