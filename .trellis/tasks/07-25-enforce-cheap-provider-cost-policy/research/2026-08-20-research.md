# Research: enforce cheap provider cost policy

Date: 2026-08-20
Scope: read-only survey of the OpenRouter provider cost/data policy surface for
the cheap PR-Agent lane, measured against this child's `prd.md`, `design.md`,
and `implement.md`.
Baseline: `npm test` → `pass 647 / fail 0` (duration 10.8s), tree clean at
`40df292`.
Parent survey: `.trellis/tasks/07-25-cheap-review-cost-controls/research/2026-08-20-research.md`
— this document does not repeat its findings, it extends them with the
provider-policy specifics this child owns.

---

## Headline

**The approach `design.md` and `implement.md` assume is not implementable
against the pinned runtime.** PR-Agent v0.39.0 does not forward OpenRouter
provider preferences, and the only extension point it has explicitly rejects
them. This is not a wiring gap that more catalog work would close; it is a
missing capability in a digest-pinned third-party container. See §3.

---

## Current State

### 1. The repository has zero provider-policy surface

`maxPrice`, `max_price`, `provider_preferences`, `providerPreferences`,
`data_collection`, `zdr`, `region`, and `parameterSupport`/`require_parameters`
return **zero hits** across `src/`, `scripts/`, and `examples/`. This confirms
the PRD background claim (`prd.md:9-13`) that the adapter supplies only model
and API key.

The complete model-facing configuration reaching the container is four
environment variables plus the credential
(`examples/pr-agent-router.yml:114-116`, `:103`):

```
CONFIG__MODEL: ${{ steps.review.outputs.model }}
CONFIG__FALLBACK_MODELS: '[]'
CONFIG__RESTRICTED_MODE: "true"
OPENROUTER__KEY: ${{ secrets.PR_AGENT_MODEL_API_KEY }}
```

and the command is bare `review` with no flags
(`examples/pr-agent-router.yml:137-139`). The `docker run` invocation forwards
an explicit `--env` allowlist (`:121-136`), so a new setting requires editing
both the `env:` block and the `--env` list — a new variable added to only one
is silently dropped.

The container is pinned by digest to
`pragent/pr-agent@sha256:cae31b51b65b5c978a3b2a978d96e89e6a4c5bcd81cb2553fd8dad0251c3a23e`
(`examples/pr-agent-router.yml:137`), documented as PR-Agent v0.39.0
(`SETUP-PR-AGENT.md:275-276`). The durable lane is byte-identical in this
respect (`examples/pr-agent-on-demand-review-router.yml:111-154`).

### 2. The catalog holds opaque handles, not constraints

`decodeRules` (`src/review-candidate-catalog.js:551-560`) declares exactly four
fields, each a `referenceValue`:

```js
price: referenceValue(rules.price, `${field}.price`),
data: referenceValue(rules.data, `${field}.data`),
promptRule: referenceValue(rules.promptRule, `${field}.promptRule`),
reasoning: referenceValue(rules.reasoning, `${field}.reasoning`),
```

`referenceValue` (`:348-352`) is documented as "an opaque, non-secret
reference … the catalog never carries the resolved value, only the handle the
private control plane resolves." So `price` and `data` are **handle names, not
policy**. There is no ceiling value, no retention predicate, and — critically —
**no `region` field and no parameter-support field anywhere in the catalog**
(grep for `region` and `parameterSupport` across `src/`: zero hits).

`design.md` and `implement.md` both name four constraint classes — price,
retention, region, and parameter-support. Two of the four have a handle; two
have nothing at all.

The catalog does carry real enforceable numbers, but they are token/cost
budgets, not provider policy: `hardInputLimit`, `hardOutputLimit`,
`hardRequestCostLimit`, `safetyMargin` with the invariant that the margin sits
below the limit (`:493-516`), plus `pricing.pricingRef` / `pricing.verified`
(`:527-530`). Those belong to the sibling token-usage child.

### 3. The pinned PR-Agent runtime cannot forward provider preferences

This is the decisive finding and it answers `prd.md:16-18` ("Research how the
pinned PR-Agent/LiteLLM OpenRouter path forwards provider routing controls").

PR-Agent v0.39.0's LiteLLM handler passes every completion call through
`_process_litellm_extra_body(kwargs)`
([`litellm_ai_handler.py`](https://github.com/qodo-ai/pr-agent/blob/v0.39.0/pr_agent/algo/ai_handlers/litellm_ai_handler.py)),
implemented in
[`litellm_helpers.py`](https://github.com/qodo-ai/pr-agent/blob/v0.39.0/pr_agent/algo/ai_handlers/litellm_helpers.py):

```python
allowed_extra_body_keys = {"processing_mode", "service_tier"}
extra_body = getattr(getattr(get_settings(), "litellm", None), "extra_body", None)
if extra_body:
    litellm_extra_body = json.loads(extra_body)
    ...
    unsupported_keys = set(litellm_extra_body.keys()) - allowed_extra_body_keys
    if unsupported_keys:
        raise ValueError(f"LITELLM.EXTRA_BODY contains unsupported keys: ...")
```

`LITELLM__EXTRA_BODY` is the one general-purpose passthrough, and its allowlist
is exactly two keys. OpenRouter carries all provider routing under a single
`provider` object, so `{"provider": {...}}` raises
`ValueError: LITELLM.EXTRA_BODY contains unsupported keys: provider` and the
review fails before any model call.

**The allowlist is unchanged on upstream `main`** (verified against the same
file on `main`), so this is not fixable by advancing the container pin to a
newer release. Every other setting the handler reads is unrelated:
`LITELLM.EXTRA_HEADERS`, `LITELLM.DROP_PARAMS`, the three callback settings,
`seed`, the Claude extended-thinking pair, `reasoning_effort`, `litellm.model_id`
(Bedrock), `temperature`, `api_base`, `ai_timeout`. None carries a `provider`
body field, and OpenRouter does not accept provider preferences via headers.

There is therefore **no configuration-only path** from this repository to
OpenRouter provider routing. Options are enumerated in Recommendations §2.

### 4. What OpenRouter actually offers (and what it does not)

From [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection):

- **`max_price`** — hard filter, caps price per million prompt/completion
  tokens. Independent prompt and completion caps, matching `design.md`'s
  "price ceilings apply independently to input and output units". **No
  account-level default exists** — it is request-only.
- **`require_parameters`** — hard filter, "only use providers that support all
  parameters". Directly satisfies the PRD's parameter-support requirement.
- **`zdr`** — hard filter for zero-data-retention endpoints. Has an
  account-level default per model-group; the per-request value ORs with it.
- **`data_collection`** (`allow`/`deny`) — documented as a **soft preference**,
  not a hard filter. Account-level default exists in privacy settings.
- **`only` / `ignore`** — hard provider-slug allow/deny lists. Account-level
  defaults exist; a request's `only` narrows within the account ceiling and
  `ignore` lists merge.
- **`quantizations`**, `allow_fallbacks`, `order`, `sort` — additional levers.
- **There is no region field.** The provider object has no geography
  constraint. The closest approximation is pinning provider slugs via
  `only`/`ignore`, which is precisely the "single endpoint pin" the PRD
  discourages (`prd.md:23-25`) and the Out-of-Scope item forbids
  (`prd.md:55-57`).
- **Failure mode**: when no endpoint satisfies the hard filters, the request
  **fails with a 404**. This is the fail-visibly primitive the PRD wants
  (`prd.md:30-32`) and it comes for free — but only if the constraints can be
  sent at all.

Two consequences for the current design: `data_collection` cannot be treated as
a hard filter (only `zdr` can), and the region constraint has no OpenRouter
primitive at all.

### 5. The account-level fallback covers three of four constraints — but not price

Because `zdr`, `data_collection`, `only`, and `ignore` all have OpenRouter
account/privacy-settings defaults, the data-policy half of this task is
enforceable today **without touching PR-Agent at all**, by configuring the
OpenRouter account that owns `PR_AGENT_MODEL_API_KEY`.

`max_price` is the exception: request-only, no account default. So the
headline deliverable — the price ceiling — is the one constraint reachable by
neither the pinned adapter nor account configuration.

### 6. Even if the catalog carried the policy, the compiler would drop it

`compileManaged` emits a frozen per-lane candidate with exactly nine fields
(`src/routed-review-compiler.js:410-420`): `candidateDigest`, `alias`, `kind`,
`handler`, `model`, `costTier`, `eligibleLanes`, `eligibleSlots`,
`promptProfile`. It carries **no** `hardRequestCostLimit`, `safetyMargin`,
`pricing`, `tokenizer`, `finishReason`, `usage`, `rules`, or `failover`.

Likewise `decodeCandidateSafeProjection`
(`src/review-candidate-catalog.js:862-963`) never exposes `rules` or
`failover` at all — the four rule handles stop at the private catalog record
(`:758-759`) and do not cross into the projection.

So the catalog → projection → compiler → adapter chain drops provider policy at
**two** independent boundaries before it could reach a workflow. Any
implementation must widen both.

### 7. There is no "policy exhaustion" outcome vocabulary

`design.md` requires failures to "fail visibly as policy exhaustion". No such
code exists:

- `PREFLIGHT_INELIGIBILITY_REASONS` (`src/review-plan-authorization.js:80-88`)
  is `capability_unavailable | head_mismatch | oversized | uncountable |
  unpriced | unit_mismatch | unenforceable`.
- `OUTCOME_REASON_CODES` (`src/protocol-v2.js:131-149`) is `completed |
  not_managed | review_none | input_ineligible | incomplete_token_limit |
  budget_overrun | policy_violation | candidate_quarantined | pool_overdrawn |
  budget_exhausted_deferred` plus seven `local_*` codes.

The nearest existing hooks are `unenforceable` (preflight — "a mandatory
constraint has no enforceable runtime mapping" fits it exactly, via
`classifyEligibility`'s `candidate.enforceable !== true` check at
`src/review-plan-authorization.js:499`) and `policy_violation` (post-dispatch
budget classification, wrong axis). Reusing `unenforceable` is likely better
than minting a new code; that is an open question, not a settled fact.

### 8. Installer and manifest state

`MANIFEST_SCHEMA_VERSION = 4` with `ROUTE_MODE_MIN_SCHEMA_VERSION = 4`
(`scripts/consumer-installer/codecs.mjs:159`, `:171`) — v4 is exactly the
route-mode feature. The managed variable table is four entries
(`:130-136`): `PR_AGENT_MODEL_PROVIDER`, `CHEAP_REVIEW_MODEL`,
`DEEP_REVIEW_MODEL`, `REVIEW_ROUTE_MODE`. There is no installer-managed field
for any cost or provider control, so consumer-side configuration for this task
would require a schema bump to v5 — following the established pattern of a
version-scoped `*_MIN_SCHEMA_VERSION` constant rather than gating on equality
with `MANIFEST_SCHEMA_VERSION` (`:170-175` documents exactly this rule).

### 9. Documentation state

`SETUP-PR-AGENT.md:230-236` already states the governing principle: "To add a
provider that needs more than one credential or an endpoint setting, extend the
workflow contract deliberately; do not construct secret names dynamically or
pass keys through the router." The OpenRouter section (`:246-270`) documents
the model IDs and the single-key mapping but says nothing about price, data
retention, or provider selection. No rollback baseline for a provider policy is
documented anywhere.

## Staleness in existing design/implement

Both artifacts were authored `2026-07-25` (`2eeca60`, repaired by `41ded21`)
and have not been touched since except for the park/resume note in `task.json`
(`85a260f`, 2026-08-15). Confirmed by
`git log -- .trellis/tasks/07-25-enforce-cheap-provider-cost-policy/`.

They contain no file/line citations, so there are no stale citations to repair.
What they carry instead are stale **assumptions**:

1. **`design.md` assumed the pinned runtime could carry the policy.** "The
   PR-Agent adapter translates the compiled policy through the pinned
   PR-Agent/LiteLLM/OpenRouter path" was written before anyone read
   `_process_litellm_extra_body`. It cannot.
2. **`design.md` and `implement.md` both list "region" as a first-class
   constraint.** OpenRouter has no region field (§4).
3. **`design.md` called retention a hard filter.** Only `zdr` is;
   `data_collection` is a soft preference (§4).
4. **`design.md` invoked "policy exhaustion" as if it were existing
   vocabulary.** It is not (§7).
5. **Neither artifact accounts for the two-boundary drop** at the safe
   projection and the compiler (§6).
6. **Neither mentions manifest v4 / route-mode**, which post-dates them, nor
   the v5 bump any consumer-side control would need (§8).

`implement.md` step 1 ("Pin and exercise the … policy-forwarding path with
representative endpoint fixtures") is the step that would have surfaced all of
this. It was correctly sequenced first; it simply had not been run.

**Verdict: both are stale on their central premise, not on their citations.**
Fixes applied in place, preserving intent — see the bottom of this document.

## Open Questions

1. **Which forwarding mechanism, given the allowlist?** Four candidates, none
   free: (a) an `api_base` shim that injects `provider` into the body,
   (b) a forked/rebuilt PR-Agent image, (c) OpenRouter account-level
   configuration for the three constraints that support it, accepting that
   `max_price` is unenforceable, (d) upstream contribution to widen the
   allowlist. Owner decision required before any code.
2. **Is a price ceiling still required if it cannot be enforced in-band?** The
   task title is "enforce cheap provider cost policy" and `max_price` is
   exactly the unreachable one. If (c) is chosen, this task delivers the data
   policy and *not* the price ceiling, and should be retitled and rescoped.
3. **Does region survive?** With no OpenRouter primitive, region is either
   dropped, or expressed as a provider-slug allowlist — which the PRD's own
   Out-of-Scope forbids. It cannot be both.
4. **New reason code or reuse `unenforceable`?** (§7). Reuse is cheaper and the
   semantics fit; minting `policy_exhausted` is clearer but touches a
   cross-cutting enum three siblings also read.
5. **Does the park still hold?** `task.json:28` conditions resuming on v1 being
   distributed to fleet consumers *and* the v2 scope being revalidated. The
   unpark was an owner directive (`unpark-all`), not a satisfaction of those
   conditions. Not probed here.
6. **How is "integration tests prove constraints reach OpenRouter"
   (`prd.md:38-40`) satisfiable in CI at all?** It implies either live billed
   calls or a recorded-fixture proxy. Nothing in `test/` does either today.

## Recommendations

1. **Do not start this task. Run `implement.md` step 1 as a spike first, and
   let its result rescope the PRD.** §3 is a capability finding about a
   third-party pinned container; every downstream step (catalog schema,
   compiler widening, acknowledgment evidence, docs) is wasted if the answer to
   Open Question #1 is (c). This is the cheapest possible ordering and the
   artifacts already put that step first.
2. **Prefer option (c) — OpenRouter account configuration — for the MVP.** It
   enforces `zdr`, `data_collection`, `only`, and `ignore` today, with zero
   repository change, zero new attack surface, and no fork to maintain. Its
   honest cost is that it is not digest-bound, not verifiable from CI, and does
   not cover `max_price`. Document it as an operational control with a named
   owner rather than pretending it is a code-enforced one.
3. **Sequence this child last of the three, as the parent survey also
   concluded.** It has the most external unknowns and the least existing code.
   The sibling output-token cap is a genuine one-variable vertical slice; this
   one is not.
4. **If in-band enforcement is required, the `api_base` shim (a) is the least
   bad of the invasive options.** It needs no fork of a digest-pinned image and
   keeps the generic-secret boundary intact. It does add a hop that sees every
   request body — which is in direct tension with the data-retention policy this
   task exists to enforce. Weigh that explicitly.
5. **Widen the safe projection and the compiler together, or neither.** §6 —
   widening one leaves policy stranded at the other boundary, which looks like
   progress and is not.
6. **Fix the `data_collection`-is-a-hard-filter error wherever it propagates.**
   It is the kind of mistake that produces a policy believed to be enforced and
   silently is not — the exact failure the PRD's "never route to a less
   restrictive endpoint silently" clause forbids.
