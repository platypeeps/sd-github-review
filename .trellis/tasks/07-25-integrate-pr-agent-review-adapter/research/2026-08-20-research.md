## Current State

### 1. PR-Agent is invoked from workflow YAML, not from `src/`

There is no PR-Agent adapter module in `src/`. Every invocation of the cheap
lane happens in a workflow template step that runs the pinned container
directly:

- Standalone lane: `examples/pr-agent-router.yml:96-139` — step
  `Run PR-Agent review`, `docker run --rm ... pragent/pr-agent@sha256:cae31b…`
  with subcommand `review` (`examples/pr-agent-router.yml:137-139`).
- Durable lane (installer-managed): `examples/sd-review.yml:116-159`, same
  container digest at `examples/sd-review.yml:157`.
- Durable on-demand variant: `examples/pr-agent-on-demand-review-router.yml`
  (181 lines; differs from `sd-review.yml` only in `name:` and the
  `independent-review-floor` default — `copilot` vs `none`).

The Action's own JavaScript never touches the reviewer. `src/index.js:1-17`
imports only `github.js`, `operations.js`, `risk-context.js`,
`reviewer-dispatch.js`, `normalize.js`, `router.js`. `src/reviewer-dispatch.js`
is 44 lines and is **Copilot-only** — a presence probe plus a conditional
`requestReviewer` call (`src/reviewer-dispatch.js:9-44`). It has no PR-Agent
path and no external-provider path at all.

### 2. What the Action contributes to the cheap lane today

The Action selects the model and emits routing outputs; the workflow does the
rest:

- `steps.review.outputs.model` feeds `CONFIG__MODEL`
  (`examples/pr-agent-router.yml:114`, `examples/sd-review.yml:134`).
- Single-target invocation is enforced by literal env, not by code:
  `CONFIG__FALLBACK_MODELS: '[]'` (`examples/pr-agent-router.yml:115`,
  `examples/sd-review.yml:135`) and `CONFIG__RESTRICTED_MODE: "true"`
  (`:116` / `:136`).
- Provider/model-prefix agreement is a shell preflight step,
  `id: pr-agent-config` (`examples/pr-agent-router.yml:63-94`), which fails
  closed on an empty model (`:70-73`) and on an unsupported provider
  (`:81-84`).
- Route-mode spend control is a separate fail-closed shell gate that refuses to
  guess a route (`examples/pr-agent-router.yml:25-41`).

### 3. Secret scoping

One secret, `PR_AGENT_MODEL_API_KEY`, is fanned into exactly one provider env
var by a conditional expression per provider
(`examples/pr-agent-router.yml:101-113`; identical block at
`examples/sd-review.yml:121-133`). Each is passed with a bare `--env NAME` so
the value never appears in the command line (`:120-136` / `:140-156`). No
volume mounts are used, which is asserted in test.

### 4. Evidence / receipt handling for the cheap lane

The durable lane uses the **v1** adapter contract, and only the v1 one:

- `src/operations.js:2-8` imports `decodeAdapterRequest`,
  `decodeAdapterAcknowledgment`, `decodeBackend`, `decodeReviewRequest`,
  `stableProtocolJson` from `src/protocol.js`.
- `decodeAdapterRequest` (`src/protocol.js:661-726`) requires
  `requestType === "routed-review-dispatch"`
  (`src/protocol.js:666-669`), `backend.kind === "external"`
  (`src/protocol.js:699-702`), and a `requestFingerprint`
  (`src/protocol.js:707-712`).
- `decodeAdapterAcknowledgment` at `src/protocol.js:728`.
- Adapter outcome vocabulary is coarse:
  `ADAPTER_OUTCOMES = success|failure|cancelled|skipped`
  (`src/operations.js:21`) mapped to `adapter-failed` / `adapter-cancelled` /
  `adapter-skipped` (`src/operations.js:22-25`).
- The workflow supplies that outcome as raw job status:
  `adapter-outcome: ${{ needs.pr-agent.result }}`
  (`examples/sd-review.yml:178`).

So today's receipt records *that the reviewer job ran and how it exited*. It
records no model actually used, no usage, no cost, no finish reason, and no
prompt-profile identity.

### 5. A-004 credential isolation — already shipped

The durable template splits three jobs with distinct permissions:

- Workflow-level: `permissions: contents: read` only
  (`examples/sd-review.yml:37-39`).
- `review` job holds `checks: write` (`examples/sd-review.yml:43-47`).
- `pr-agent` job holds only `contents: read` + `pull-requests: write` — no
  `checks`, no `issues` (`examples/sd-review.yml:69-77`), with the rationale in
  the comment at `examples/sd-review.yml:34-36` and `:73-74`.
- `finalize` job re-acquires `checks: write`
  (`examples/sd-review.yml:161-169`) and exchanges only the bounded
  acknowledgment (`examples/sd-review.yml:171-186`).

This is test-enforced: `test/metadata.test.js:245-267` asserts each job's exact
permission map and explicitly asserts
`jobs["pr-agent"].permissions.checks === undefined` and
`.issues === undefined`. The same block asserts the pinned digest, absence of
`-v/--volume/--mount/--volumes-from`, absence of `/github/workspace`, the
per-provider secret expression, `CONFIG__FALLBACK_MODELS === "[]"`, and
`CONFIG__RESTRICTED_MODE === "true"`
(`test/metadata.test.js:268-296`). The archived task
`08-04-isolate-pr-agent-receipt-authority` is `completed` (2026-08-04).

### 7. Which PRD primitives already exist as contracts

The *verifier* side is largely built; the *producer* side is not.

- Prompt-profile binding (referenced vs handler-managed, with
  default/inheritance/fallback/commandOverride/runtimeOverride explicitly
  rejected): `src/protocol-v2.js:494-519`.
- Prompt-profile **metadata** registry (alias/version/digest +
  `compatibleHandlers` + `capabilities`): `decodePromptProfileRegistry`,
  `src/review-candidate-catalog.js:633-676`. Its own comment at
  `src/review-candidate-catalog.js:629-631` states the actual template and
  PR-Agent configuration values are *adapter-owned and keyed by the same
  identity* — i.e. deliberately out of that module.
- Exact-digest + handler-compatibility resolution against the registry:
  `resolveProfileBinding`, `src/review-candidate-catalog.js:695`.
- Candidate preflight **decoder** with `countedInputTokens`, `inputCounted`,
  `outputCap`, `maxExpectedCharge`, `hardRequestLimit`, `safetyMargin`,
  `capabilityEvidence`, and the `maxExpectedCharge <= hardRequestLimit`
  invariant: `decodeCandidatePreflight`, `src/protocol-v2.js:669-726`.
- `incomplete_token_limit` is an existing reason code:
  `src/protocol-v2.js:136`.
- Plan authorization binds candidate digest ↔ preflight digest ↔ prompt-profile

  `src/review-plan-authorization.js:440-488`; control-plane response

Every one of these **consumes** a preflight object. Nothing in the repo

## Gaps vs PRD

Ordered by how much of the acceptance criteria they block.

**G1 — No adapter component exists.** Every PRD requirement that says "the
adapter resolves / prepares / dispatches / returns" has no code home. The
reviewer is a `docker run` line in YAML
(`examples/sd-review.yml:140-159`), not a component that can resolve a profile,
prepare a request, or return structured evidence. Blocks essentially all of
Acceptance Criteria 1-9.

**G2 — No private profile-value store.** PRD requires resolving the exact
profile identity "through the private adapter registry" and applying the
profile. The identity registry exists
(`src/review-candidate-catalog.js:633-676`) but by design carries no template
or PR-Agent config values (`src/review-candidate-catalog.js:629-631`). The
adapter-owned store keyed by alias/version/digest does not exist anywhere in
the repo. Blocks AC-4, AC-5.

**G3 — No preflight producer.** PRD requires a side-effect-free preflight that
prepares the complete request and returns counted input, output cap,
price/unit evidence, conservative maximum charge, hard request limit, prepared-
request fingerprint, and capability evidence. Only the decoder/verifier exists
(`src/protocol-v2.js:669-726`). Nothing counts tokens, nothing knows prices,
nothing renders a prepared request. Blocks AC-8.

**G4 — No structured acknowledgment from the reviewer.** PRD requires
returning configured/actual model, provider, dispatch state, applied
prompt-profile alias/version/digest, finish reason, usage/cost reference,
policy digest, bounded limitations. Today the acknowledgment carries a job
status string (`examples/sd-review.yml:178`,
`src/operations.js:21-25`). PR-Agent's stdout is not captured, parsed, or
bound to anything. Blocks AC-2, AC-6 (partially), AC-9.

**G5 — Output cap is not applied and `incomplete_token_limit` is never
emitted.** No `CONFIG__` env in either template sets an output/token cap
(`examples/pr-agent-router.yml:114-117`, `examples/sd-review.yml:134-137` set
only model, fallback list, restricted mode, PR number). The reason code exists
(`src/protocol-v2.js:136`) but is unreachable. Blocks AC-9.

**G6 — Same-model endpoint failover is untested and unimplemented.** PRD/AC-1
require proving supported same-model endpoint failover and cross-model
substitution rejection. Cross-model rejection is achieved bluntly by
`CONFIG__FALLBACK_MODELS: '[]'`; there is no provider-router concept in the
repo at all, so "policy-compliant same-model endpoints" has no implementation

owner — `07-25-enforce-same-model-provider-failover` was dropped as rejected on

## Staleness in existing design/implement

`design.md` and `implement.md` are dated 2026-07-25 and contain **zero file or
line citations**, so nothing in them is factually wrong in the "cites a moved
symbol" sense. The staleness is different in kind: they were written before the
v2 contract modules landed and before A-004 shipped, so they describe as
future work several things that now exist, and they silently assume a
distribution posture that no longer holds.

Specific drift:

1. **A-004 isolation is described as in-scope work** (PRD requirement bullet at
   `prd.md:26-29`, AC-7 at `prd.md:51-53`). It shipped on 2026-08-04
   (`examples/sd-review.yml:34-77`, `:161-186`;
   `test/metadata.test.js:245-267`). `design.md` does not mention it as done.
2. **`design.md` "Prompt-Profile Resolution"** describes registry resolution,
   digest verification, and substitution rejection as adapter work. The
   *identity* half of that is delivered
   (`src/review-candidate-catalog.js:633-676`, `:695`;
   `src/review-plan-authorization.js:440-462`); only the *value* half remains.
   The design does not distinguish the two, which risks re-implementing the
   delivered half.
3. **`design.md` preflight paragraph** describes the preflight field set almost
   exactly as `decodeCandidatePreflight` already encodes it
   (`src/protocol-v2.js:669-726`) without noting the contract exists. The real
   remaining work is the producer, not the shape.
4. **`design.md` "cross-model fallback disabled"** is delivered
   (`examples/pr-agent-router.yml:115`, `examples/sd-review.yml:135`,
   asserted `test/metadata.test.js:293`).
5. **Neither document acknowledges the reachability problem.** 9,390 of 13,136
   `src/` lines are unreachable from `src/index.js`. An adapter built against
   `review-plan-authorization.js` inherits that unreachability and ships dead
   on arrival. This is the single most consequential omission.
6. **Neither document mentions manifest schema v4 or installer-managed
   `REVIEW_ROUTE_MODE`**, which is now the operative spend control
   (`scripts/consumer-installer/codecs.mjs:122`, `:171`;
   `.github/sd-github-review.json:32`). Any adapter that changes how the cheap
   lane is entered has to route through the installer, not through hand-edited
   YAML.
7. **`implement.md` step 1** ("add fixtures") is partly delivered:
   `fixtures/protocol/v2/prompt-profile-registry.{valid,invalid}.json`,
   `candidate-safe-projection.*`, `candidate-options.*`,
   `routed-review-handler-profiles.valid.json` all exist and are exercised by
   `test/review-candidate-catalog.test.js:30-31,125-133` and
   `test/routed-review-compiler.test.js:19-28`. What is missing is
   request-preflight, token-boundary, and secret-boundary fixtures.

**Verdict — `design.md`: partially stale.** Intent is intact and still correct;
it over-scopes (claims delivered work as pending) and under-scopes (omits the
reachability blocker and the installer/route-mode surface). Needs annotation,
not rewriting.

**Verdict — `implement.md`: materially stale.** Steps 1 and 4 are partly
delivered; the plan has no step for the private profile-value store, no step
for capturing PR-Agent output, and no step addressing entrypoint reachability —
which is a prerequisite, not a detail. Needs a reordered plan.

## Open Questions

1. **Does the park still hold?** `task.json` `notes` records the resume
   condition as: v1 actually distributed to fleet consumers AND v2-governance
   scope deliberately revalidated. Reachability is unchanged at this HEAD
   (verified above). Consumer deployment was **not** re-probed in this pass —
   the 2026-08-15 check found `rwbp-coordinator`, `loadsmith`, `hoa-manager`,
   `anomaly-metric-creator` all 404 for `config/routed-review-setup-v1.json`.
   Someone should re-probe before implementation starts.
2. **Where does the private profile-value store live?** Options: a repo file
   consumed at build time, a step in the reviewer job, or a separate private
   package. The PRD says "private", which argues against a repo file, but the
   digest must be verifiable by the Action, which argues against a runtime-only
   secret. This is undecided and blocks G2.
3. **How is PR-Agent output captured?** The container writes its review to the
   PR via `GITHUB__USER_TOKEN` and prints to stdout. Getting model/usage/finish
   reason back requires either parsing stdout, a PR-Agent output flag, or a
   LiteLLM callback. None is currently investigated.
4. ~~**Is "same-model endpoint failover" (AC-1) still wanted?**~~ **Answered —
   no.** *Corrected 2026-08-20 (adversarial review, C-7): this pass raised it as
   open without checking the consolidation record, where it was already settled.*
   `07-25-enforce-same-model-provider-failover` was dropped as rejected on
   2026-08-08
   (`.trellis/tasks/archive/2026-08/08-08-backlog-consolidation/prd.md:82`),
   together with `07-25-qualify-cheap-review-candidates`,
   `07-25-govern-cheap-review-fallbacks`,
   `07-25-control-cheap-review-reasoning-effort`, and
   `07-25-evaluate-cheap-provider-failover-pilot` — the entire "provider failover
   governance" cluster, and the same set `prd.md:61-62` names as this task's
   candidate-policy dependency. Rationale at `:96-99`. AC-1's failover clause and
   that Dependencies line should be struck by the owner.
5. **Should the adapter be a `src/` module or a workflow-composed step?**
   Everything the PRD asks for (preflight before reservation, digest binding,
   structured acknowledgment) points to `src/`; everything currently shipping
   points to YAML. This is the central design decision and neither artifact
   makes it.

## Recommendations

1. **Close G7 first — it is independent and cheap.** Add `sd-review.yml` to the
   workflow list in `test/metadata.test.js:170-174` so the actually-installed
   durable template carries the A-004 assertions. This is a few lines and does
   not depend on any v2 decision.
2. **Resolve the reachability question before writing adapter code.** Either
   (a) wire a v2 entry path from `src/index.js` so new work is reachable, or
   (b) accept that this task produces library code and say so explicitly in
   `design.md`. Silently building more unreachable code is the failure mode the
   park was created to prevent.
3. **Re-probe fleet consumers for `config/routed-review-setup-v1.json`** before
   unparking in practice. The unpark was an owner directive, not a premise
   falsification.
4. **Split the task.** The current PRD bundles at least four separable
   deliverables: (i) private profile-value store + digest verification,
   (ii) preflight producer, (iii) reviewer output capture / structured
   acknowledgment, (iv) output cap + `incomplete_token_limit`. Only (iii) and
   (iv) are useful without the v2 plan machinery being reachable — and they are
   the two with real user-visible value today.
5. **Mark delivered scope explicitly** in `design.md` / `implement.md` rather
   than deleting it, so the next reader does not re-derive it. Done in this
   pass — see the `DELIVERED` annotations.
6. **Reconsider AC-1's failover clause** (Open Question 4) before it becomes a
   fixture-writing obligation.
