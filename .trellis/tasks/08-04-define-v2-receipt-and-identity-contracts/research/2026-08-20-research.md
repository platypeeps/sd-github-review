## Gaps vs PRD

### B-1 (BLOCKING) — the planned retention import is forbidden by a shipped layering test

`implement.md` step 1 adds an import of `RETENTION_DATA_CLASSES` /
`RETENTION_LIFECYCLE_STATES` / `DELETION_STATUSES` from `./retention-policy.js` into
`src/protocol-v2.js`. `design.md` §3 (C-6) clears this on the grounds that there is
no import cycle, which is true.

But `test/dependency-boundaries.test.js:18-55` freezes an explicit allowed-import
matrix, and line 24 reads:

```js
"protocol-v2.js": ["protocol.js"],
```

The test at `:98` (`"each module imports only modules to its right in the layering"`)
walks every `from "./x.js"` in each module and asserts membership. Adding the
retention import makes it fail with
`src/protocol-v2.js imports src/retention-policy.js, which the layering forbids`.

Consequences for the plan as written:

1. The import cannot land without also editing `test/dependency-boundaries.test.js:24`
   to `["protocol.js", "retention-policy.js"]`.
2. That edit falsifies design.md's Compatibility section ("No existing decoder,
   fixture, signature, or `retention-policy.js` line changes") and implement.md's
   Rollback ("No existing decoder, fixture, signature, or `retention-policy.js` line
   is mutated") — an existing TEST file must change, which the rollback shape did not
   account for.
3. It is a deliberate layering decision, not a mechanical fix: the matrix comment at
   `:6-11` says it exists precisely to stop a future edit from silently re-inverting
   the layering. `retention-policy.js` is a leaf (`:25` lists `[]`), so
   `protocol-v2.js → retention-policy.js` is a legal leftward edge in principle; the
   matrix simply has not authorized it.

Alternative that avoids the edit entirely: declare the three vocabularies
protocol-locally in `protocol-v2.js` and add a drift test asserting they deep-equal
the `retention-policy.js` exports. That trades C-6's single-source-of-truth for a
zero-layering-change footprint. This is an owner decision; I have not made it.

### B-2 (MATERIAL) — a safe catalog projection with per-candidate prompt profiles already ships

`design.md` §3 "Projection authority — scope bound (C-1)" justifies creating
`decodeSafeCatalogProjection` by observing that `decodeReviewerCatalog` carries no
per-candidate prompt profile, and that `promptProfile` appears in `protocol-v2.js`
only at 494/557/562/587-589/714. Both statements verify exact — **scoped to
`protocol-v2.js`**. One module over, the thing the design is about to build already
exists:

- `src/review-candidate-catalog.js:862` — `decodeCandidateSafeProjection(value, field)`.
  Returns a frozen record with `catalogDigest` (`:915`), `alias` (`:916`), and
  `promptProfile: {mode, alias, version, digest, compatibleHandlers, capabilities}`
  (binding decoded at `:888`, projected at `:899-911`, frozen at `:939-944`), plus
  `eligibleLanes`/`eligibleSlots`/limits/tokenizer/pricing.
  It is the *per-candidate* granularity.
- `src/routed-review-compiler.js:274` — `decodeCatalogProjection(value, field, expectedCatalogDigest)`.
  Decodes the *array* form: `{schemaMajor, catalogDigest, candidates:[...]}`, binds the
  catalog digest exactly (`:279-281`), enforces non-empty + `MAX_COLLECTION_ITEMS`
  (`:282-287`), and rejects duplicate candidate content digests (`:295-298`). This is
  structurally the `decodeSafeCatalogProjection` design §2 specifies.
- Fixtures already exist: `fixtures/protocol/v2/candidate-safe-projection.{valid,invalid}.json`
  and `fixtures/protocol/v2/routed-review-catalog-projection.valid.json`.
- Tests already exist: `test/review-candidate-catalog.test.js`, `test/routed-review-compiler.test.js`.

Differences that mean it is not a drop-in substitute:

- It uses `schemaMajor`, not `schemaVersion`.
- It carries **no `candidateDigest` field** — identity is `alias` plus a derived
  content digest (`deriveCatalogDigest(projection)`, `review-candidate-catalog.js:465`,
  used at `routed-review-compiler.js:295`). Design §3's B2 join key is
  `(alias, candidateDigest)`, which this projection does not expose directly.
- It carries `compatibleHandlers` and `capabilities`, which design §6 explicitly says
  the projections should NOT carry.

So the design's decision is defensible, but it was made without knowing the
alternative existed. Left as an open question rather than resolved unilaterally.

### B-3 (MATERIAL) — the cross-artifact profile checks design §6 plans are partly shipped

`design.md` §6 defines "digest-mismatched" and "incompatible" as cross-artifact
full-record membership failures between a catalog projection and a compiled entry,
and states these are new. `src/routed-review-compiler.js:367` `compileManaged`
already does exactly this at the contract layer:

- `:383-386` — a lane candidate absent from the catalog projection throws
  `references a candidate absent from the catalog projection` (`:385`) — the design's
  **unknown** case.
- `:404-406` — `bindingsEqual(laneValue.candidate.promptProfile, candidate.promptProfile)`
  throws `does not match the catalog candidate's exact prompt-profile identity` (`:405`)
  — the design's **digest-mismatched** and **incompatible** cases for a compiled entry.
- `:393-398` — lane eligibility (`:394`) and slot eligibility (`:397`) checks.

Additionally, `decodeCandidateSafeProjection` enforces handler compatibility inside
the contract boundary: `review-candidate-catalog.js:950-951` throws
`promptProfile.compatibleHandlers must include the candidate handler for a referenced
projection`. Design §6 declares handler-registry compatibility "compiler/runtime
territory and OUT OF SCOPE", and explicitly narrows
`research/v2-receipt-identity-surface.md:118` on that basis. That narrowing is
contradicted by shipped code: `compatibleHandlers` matching is already a
contract-layer check in this repo.

What is genuinely NOT covered anywhere today, and remains this task's real delta:
the same membership/mismatch checks **for a receipt and for a durable
authorization**. prd line 27's "across the catalog/compiled/authorization/receipt
contracts" is half-satisfied by `compileManaged` on the catalog↔compiled edge, and
entirely unsatisfied on the authorization and receipt edges.

blocking; just undocumented.

## Recommendations

1. **Resolve B-1 before `task.py start`.** It is the only finding that makes the plan
   fail as written. Whichever way it goes, implement.md step 1 needs the decision
   recorded, and the gate list should add `npx node --test test/dependency-boundaries.test.js`
   as an explicit early check so the failure surfaces in step 1 rather than at the
   final gate.
2. **Resolve B-2/B-3 together.** They are one question — "how much of this already
   exists in the catalog/compiler layer?" — and the answer changes the size of the
   task materially. If `compileManaged` covers the compiled edge, the remaining work
   is the receipt and authorization edges plus the receipt's retention projection,
   which is a meaningfully smaller and better-motivated delta.
3. **Take B-4, B-7 as mechanical.** Rename or alias; update the count.
4. **Restate the AC5 gate line (B-5) honestly.** A gate that does not measure the
   code under change should not be cited as evidence that the code is covered. Either
   scope a coverage run to the file or say plainly that coverage is unmeasured here.
5. **Keep design.md's core.** The B2 candidate-identity decision, the full-body
   fingerprint scope (C-5), the C-2 sharing-vs-membership distinction, and the C-3
   retention-vocabulary-not-field-list note are all correct and well-evidenced against
   current code. Nothing found in this pass argues for reopening them.
