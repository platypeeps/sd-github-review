## Current State

### Two different things are called "standalone"

This is the single most important fact for anyone picking the task up, and it is
not recorded in any of the task documents.

1. **v1 `operation=standalone`** — the shipped Action's *default operation*,
   meaning "event-driven routing" as opposed to the durable operations
   (`receipt`, `check`, `adapter-request`, ...). Entry at
   `src/index.js:147` (`normalizeOperation(input("operation", "standalone", env))`)
   and branched at `src/index.js:148`; emitted verbatim as an output value at
   `src/index.js:117`. Also `src/operations.js:235`, `src/operations.js:533`, and
   `scripts/validate-action-metadata.mjs:392,402`.
2. **v2 `mode: standalone`** — this task's concept, the discriminated
   no-control-plane mode. Defined at `src/protocol-v2.js:29`
   (`SOURCE_MODES = ["standalone", "managed"]`).

The collision extends to the word `mode`. `src/index.js:161` reads
`normalizeMode(input("mode", "auto", env))`, which is the *route* mode
(cheap/deep/copilot/auto) validated at `src/normalize.js:17-23` — unrelated to
the v2 source mode. The PRD requirement "never an inferred `auto` mode" reads as
a direct contradiction of shipped behavior unless the reader knows these are two
different `mode` namespaces.

Implementation implication: the v2 mode cannot be introduced as an input named
`mode`, and `mode=standalone` receipts/checks must not be confused with the
existing `operation=standalone` output value.

## Gaps vs PRD

Ordered by how much they block the rest.

1. **No v2 attempt receipt contract at all.** `src/protocol-v2.js` has
   `decodeLocalReviewReceipt` (`:1258`) and `decodeHistoricalV1Receipt`
   (`:1774`), but no general attempt receipt. The PRD requires receipts carrying
   `mode=standalone`, execution kind, handler/profile or local-attestation
   provenance, known limitations, and `budgetOutcome=not_managed`. `src/receipt.js`
   is the v1 receipt and contains no `mode` field.
2. **`decodeCheckProjection` carries no mode** (`src/protocol-v2.js:1324-1345`).
   Fields are `checkName, headSha, conclusion, revision, attempt,
   latestAuthorizedAttemptToken`. The PRD requires mode and provenance in checks,
   and requires deriving assurance/gate from either a direct fixed review or a
   valid exact-head local attestation. The check *names* exist
   (`protocol-v2.js:153-154`) but nothing projects a standalone check.
3. **`decodeSetupDiscoveryV2` carries no mode** (`src/protocol-v2.js:1397-1445`).
   Fields are `activeMajor, checks, gateOnlyBranchProtection,
   optionalCapabilities`. The PRD requires setup discovery to report mode and
   known limitations. Note `fixtures/setup/v2/discovery.valid.json` matched a
   standalone-vocabulary grep, so the fixture may already be ahead of the decoder
   — worth a direct diff before writing new fixtures.
4. **`/review options` has no standalone arm.**
   `decodeCandidateOptionsResponse` (`src/protocol-v2.js:763-793`) *requires*
   `catalogDigest` and `configurationDigest` and returns candidate aliases —
   exactly what the PRD forbids standalone from advertising. There is no
   standalone options shape and no `unsupported_in_standalone` response for
   budget/pending/recovery/quarantine/adjudication/parallel operations.
5. **The consumer installer is completely mode-unaware.** A grep for
   `standalone` across `scripts/` returns only the two v1 `operation` hits in
   `validate-action-metadata.mjs:392,402`. Nothing in
   `scripts/consumer-installer.mjs` or `scripts/consumer-installer/*.mjs` knows
   about v2 modes. No scaffolding, no v1-to-standalone migration, no semantic
   mode diff, no managed-outage no-fail-open path. This is the largest single
   chunk of unstarted work and covers PRD criteria 1 and 7.
6. **No standalone planning arm.** `implement.md` step 3 requires standalone to
   emit one immutable direct-handler plan or await one bounded local
   attestation. `review-plan-authorization.js` is managed-only by construction.
7. **No documentation.** `README.md` mentions "standalone" once
   (`README.md:147`) and it is the v1 operation sense. `DESIGN.md` discusses
   standalone at `:80-81, :146, :156, :252-253, :403, :417` all in the v1 sense,
   and at `:432` calls standalone external routing "a compatibility mode" while
   `:437` says "Version 2 **plans** an explicit standalone `local-attested`
   route" — future tense, now stale relative to the shipped decoder. No
   capability matrix anywhere outside this task's `design.md`.

## Open Questions

1. **Is the v2 scope still wanted?** The park was lifted by owner directive
   (`unpark-all`), not by the park's own resume condition, which required v1 to
   be distributed to fleet consumers *and* v2 governance scope to be
   deliberately revalidated. The 2026-08-15 re-verification found zero fleet
   consumers carrying `config/routed-review-setup-v1.json`
   (`rwbp-coordinator`, `loadsmith`, `hoa-manager`, `anomaly-metric-creator` all
   404). I did not re-probe those consumers. If distribution is still zero, this
   task adds a seventh unreachable module to a codebase that is already 71%
   unreachable.
2. **Does anything intend to wire `protocol-v2.js` into `src/index.js`?** No
   active task in `.trellis/tasks/` obviously owns that edge. Without it,
   completing this task's remaining seven acceptance criteria produces more
   dead code, however well tested.
3. **Scope overlap with `07-25-support-local-attested-reviews`** (sibling, also
   `status: planning`). Both this PRD and that one own the `local-attested`
   route, its trust policy, and its assurance/gate projection. The boundary is
   not stated in either document. `protocol-v2.js` already has
   `decodeLocalAttestationRequest` (`:1182`), `decodeLocalReviewAuthorization`
   (`:1211`), `decodeLocalReviewReceipt` (`:1258`), and
   `decodeLocalAttestationStatus` (`:1292`) — so the sibling appears to have
   landed its contracts, and this task should consume rather than redefine them.
4. **Which `mode` name does the v2 source input take?** `mode` is occupied by
   route mode at `src/index.js:161`. Needs a decision (`review-mode`,
   `source-mode`, config-file-only) before installer work starts.

## Recommendations

1. **Do not archive.** Five of eight acceptance criteria are untouched, and the
   completed child covered unrelated v1 routing.
2. **Settle open question 1 before writing code.** The task's own park
   rationale set a resume condition that the `unpark-all` directive bypassed. Re-probe
   the four fleet consumers for `config/routed-review-setup-v1.json`; if all
   still 404, the honest options are re-park or a deliberate scope decision, not
   silently continuing.
3. **If work proceeds, sequence by leverage:** the reachability edge from
   `src/index.js` first (open question 2), then the receipt/check/setup-discovery
   mode fields (gaps 1-3, which unblock PRD criteria 2, 3, 6), then the installer
   (gap 5, criteria 1 and 7), then docs (gap 7, criterion 8).
4. **Resolve the naming collision explicitly** and record the chosen input name
   in `design.md` before any installer or action-metadata change.
5. **Deconflict with `07-25-support-local-attested-reviews`** before
   implementing anything local-attested; treat that task's contracts as the
   source of truth.
