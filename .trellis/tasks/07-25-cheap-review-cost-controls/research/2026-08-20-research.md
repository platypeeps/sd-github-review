### 2. The cheap lane's actual cost surface is four environment variables

Both shipped workflow shapes run PR-Agent as a pinned Docker image with an
identical, minimal configuration:

- Event-driven: `examples/pr-agent-router.yml:96-139`
- Durable/on-demand: `examples/pr-agent-on-demand-review-router.yml:111-154`

The complete model-facing configuration is:

```
CONFIG__MODEL: ${{ steps.review.outputs.model }}      # pr-agent-router.yml:114
CONFIG__FALLBACK_MODELS: '[]'                         # pr-agent-router.yml:115
CONFIG__RESTRICTED_MODE: "true"                       # pr-agent-router.yml:116
OPENROUTER__KEY: <secret>                             # pr-agent-router.yml:103
```

and the command is bare `review` with no flags
(`examples/pr-agent-router.yml:138-139`, and identically
`examples/pr-agent-on-demand-review-router.yml:153-154`).

`CONFIG__FALLBACK_MODELS: '[]'` is already set in both workflows, which
satisfies the parent PRD's standing requirement to keep it empty. Everything
else the parent PRD asks for is absent:

- **No token controls.** No `max_tokens`, no `custom_model_max_tokens`, no
  input budget. Verified by grep across `src/`, `scripts/`, `examples/`.
- **No price/provider controls.** `maxPrice`, `max_price`,
  `provider_preferences`, `providerPreferences`, `data_collection`, and `zdr`
  return **zero hits** across `src/`, `scripts/`, and `examples/`. This directly
  confirms the `enforce-cheap-provider-cost-policy` PRD background claim
  (its `prd.md:10-12`) that the adapter supplies only model and API key.
- **No prompt profile.** The bare `review` command uses PR-Agent's stock review
  configuration, confirming the `reduce-cheap-review-prompt` PRD background
  claim (its `prd.md:10-13`).
- **No reasoning-effort control.**

The model itself comes from the repository variable `vars.CHEAP_REVIEW_MODEL`
passed as the `cheap-model` input (`examples/pr-agent-router.yml:49`), i.e. a
mutable consumer-side GitHub variable, **not** a pinned catalog entry. The
workflow's only guard is a string-prefix check that the model id matches the
declared provider (`examples/pr-agent-router.yml:63-94`).

### 3. The v1 acknowledgment carries no cost evidence

`buildAdapterAcknowledgment` (`src/operations.js:242-259`) accepts exactly four
outcomes — `success`, `failure`, `cancelled`, `skipped` — and emits
`status: acknowledged | failed` plus an optional `errorCode`. There is no field
for token counts, finish reason, reserved or actual cost, or model actually
used. The v1 adapter request (`decodeAdapterRequest`, `src/protocol.js:661+`)
likewise carries identity, route, and backend, but no economics.

So today a cheap review that terminated because it hit an output length limit is
indistinguishable, in the durable receipt, from a clean completed review. That
is precisely the failure mode the parent PRD's fifth acceptance criterion
forbids.

### 4. The unreachable v2 layer already implements most of the child contracts

This is the single most important finding for planning. The contracts the three
child PRDs describe are, at the decode/reduce level, **already written and
already tested** — they are simply not wired to anything the Action runs.

**Token/cost vocabulary** (`src/protocol-v2.js:131-149`) — `OUTCOME_REASON_CODES`
already contains `input_ineligible`, `incomplete_token_limit`, `budget_overrun`,
`policy_violation`, `candidate_quarantined`, `pool_overdrawn`, and
`budget_exhausted_deferred`. Note the spelling: the code uses
`input_ineligible`, whereas `bound-cheap-review-token-usage/prd.md:28-29` asks
for a candidate marked `ineligible_pre_dispatch` with reason
`input_token_limit`. **The PRD's outcome spelling does not match the code.**
Note this is narrower than a two-vocabulary conflict: the code already has two
axes, `OUTCOME_REASON_CODES` (`src/protocol-v2.js:131-149`) and the separate
`PREFLIGHT_INELIGIBILITY_REASONS` (`src/review-plan-authorization.js:80-88`),
so an outcome plus a preflight reason is the implemented factoring too. Only the
outcome *name* `ineligible_pre_dispatch` is absent from the code, and
`bound-cheap-review-token-usage/design.md:66-69` has already adopted
`input_ineligible` in its place. What remains is amending the child PRD line, not
choosing between two designs.

**Budget ledger** (`src/review-budget-ledger.js`) — implements
`reserve` (`:755`), `authorize` (`:872`), `releaseReservation` (`:933`),
`expireLeases` (`:953`), `reconcile` (`:981`), `applyObservation` (`:1041`),
`adjustPool` (`:1097`), `quarantineCandidate` (`:1135`),
`releaseQuarantine` (`:1150`), `projectPool` (`:1170`). Pool states are
`usable | overdrawn` (`:62`); ineligibility reasons are bounded and fail-closed
(`:88-96`), including `pool_overdrawn` and `candidate_quarantined`. Lease states
cover `reserved | authorized | released | expired | settled` (`:74-81`).

**Usage reconciliation** (`src/review-usage-reconciliation.js`) —
`BUDGET_CLASSIFICATIONS` is exactly `within_reserve | budget_overrun |
policy_violation` (`:79-83`), the three-way split
`bound-cheap-review-token-usage/prd.md:44-50` requires. `REVIEW_ASSURANCES` is
`completed | incomplete | ambiguous` (`:66`), and
`RECONCILIATION_SIDE_EFFECTS` is `none | review_published | ambiguous` (`:71`)
— the "a reviewer side effect and spend occurred" distinction is modelled.
`reconcileUsage` (`:893`) and `releaseUnusedReserve` (`:913`) are the reducers.

**Candidate catalog** (`src/review-candidate-catalog.js`) — carries the
enforceable policy the children want to store:
`hardRequestCostLimit` and `safetyMargin` with the invariant that the margin
must sit below the limit (`:505-516`); a `tokenizer` block with
`tokenizerId`/`counting`/`verified` (`:495`, `:520-523`); `finishReason`
capability evidence (`:533`); `costTier`, `budgetRef`, and `reserve`
(`:750-756`). Its `decodeRules` (`:551-560`) holds four **opaque references** —
`price`, `data`, `promptRule`, `reasoning` — and `referenceValue`
(`:348-352`) documents that "the catalog never carries the resolved value, only
the handle the private control plane resolves." The safe projection
(`decodeCandidateSafeProjection`, `:862-963`) refuses to expose an unverified
tokenizer (`:867-871`) or unverified pricing (`:874-876`).

Critically, the four rule handles map one-to-one onto the children:
`price` + `data` → `enforce-cheap-provider-cost-policy`; `promptRule` →
`reduce-cheap-review-prompt`; `reasoning` → the never-created reasoning-effort
child. The catalog was designed against the full five-child shape.

**Same-model failover** (`src/review-candidate-catalog.js:538-549`) —
`decodeFailover` hard-requires `sameModelOnly === true` and bounds
`maxAlternates` to 0-8. The comment states a cross-model failover "would
silently change review behavior and fails closed." This is the core contract of
the never-created `govern-cheap-review-fallbacks` child, already implemented.

**Prompt profiles** (`src/review-candidate-catalog.js:633-791`) — a profile
registry (`:633`), a discriminated `referenced | handler-managed` binding
(`src/protocol-v2.js:47`), a rule that external candidates must reference a
profile and native candidates must be handler-managed (`:733-739`), digest
comparison across catalog transitions (`:1016-1026`), and an explicit
`FORBIDDEN_BINDING_LEVERS` list rejecting all eleven of `default`,
`laneDefault`, `inheritance`, `inherit`, `merge`, `fallback`, `substitute`,
`substitution`, `commandOverride`, `runtimeOverride`, `override`
(`:566-580`). That list is a near-verbatim implementation of
`reduce-cheap-review-prompt/prd.md:31-33`.

**Compiler** — `compileRoutedReviewConfiguration`
(`src/routed-review-compiler.js:442`) plus `candidateProjectionDigest` (`:211`)
produce the compiled safe projection the adapter is meant to apply.

### 5. Installer and manifest state

`MANIFEST_SCHEMA_VERSION = 4` (`scripts/consumer-installer/codecs.mjs:159`),
with `ROUTE_MODE_MIN_SCHEMA_VERSION = 4` (`:171`) — so route-mode management is
exactly the v4 feature. `ROUTE_MODES` is
`auto | cheap | deep | copilot | none` (`:122`). The installer resolves route
mode with a three-source precedence — explicit option, manifest value, then the
observed `REVIEW_ROUTE_MODE` repository variable — in `routeModeForRun`
(`scripts/consumer-installer.mjs:204-213`), and a manifest below v4 produces
"manifest predates route-mode management; run update to record
REVIEW_ROUTE_MODE" (`scripts/consumer-installer.mjs:477`).

There is **no installer-managed field for any cost control** — no token cap, no
price ceiling, no profile binding, no catalog reference. Any child that needs
consumer-side configuration will require a manifest schema bump to v5.

## Parent vs child scope split

The parent PRD is explicit at `prd.md:93-96`:

> Coordination-only parent (2026-07-25 reconciliation): tracks the five child
> deliverables and cross-child acceptance; no direct implementation — start
> children, not this parent. **PRD-only is appropriate for this parent.**

So the boundary is: **children own every line of implementation; the parent owns
only cross-child invariants, sequencing, and integrated acceptance.** The
parent-level `design.md` and `implement.md` produced alongside this research are
therefore integration-and-sequencing documents, not implementation plans, and
they should not be read as reversing the coordination-only decision. See Open
Questions #1.

Three cross-child invariants belong to the parent because no single child can
enforce them alone:

1. **One reservation per dispatch.** The token child reserves; the price child
   constrains what the reservation is computed against; the prompt child changes
   the input size the reservation is computed from. All three write to the same
   `hardRequestCostLimit` / `safetyMargin` pair
   (`src/review-candidate-catalog.js:505-516`). Only the parent can hold the
   invariant that they compose to one number.
2. **No post-dispatch fallback, from any cause.** Token ineligibility, price
   exhaustion, and profile mismatch each independently tempt a "try the next
   candidate" path. The parent PRD forbids it after dispatch
   (`prd.md:26-29`); each child restates it; nobody tests the composition.
3. **The safe-projection boundary.** Every child stores policy in the pinned
   private catalog and consumes only the compiled projection. The projection
   decoder's refusals (`src/review-candidate-catalog.js:862-963`) are the
   shared chokepoint.

## Open Questions

1. **Should this parent have `design.md` and `implement.md` at all?** Its own
   PRD says PRD-only is appropriate (`prd.md:93-96`). They were created on
   explicit instruction for this run. If the coordination-only decision still
   stands, these two documents are the exception and should be labelled as
   integration artifacts — which they are. Owner should confirm rather than let
   the contradiction sit unresolved.
2. **Two of five children do not exist.** `govern-cheap-review-fallbacks` and
   `control-cheap-review-reasoning-effort` appear in `prd.md:70-71` and in the
   internal-order dependency at `prd.md:82-84`, but have no task directory and
   nothing in `.trellis/tasks/archive/`. `task.json:21-25` lists only the three
   that exist. Either the PRD is stale or two tasks were lost. Note that both
   missing children have *contract-level support already implemented*
   (`decodeFailover` at `src/review-candidate-catalog.js:538-549`; the
   `reasoning` rule handle at `:559`), which suggests they were real and got
   dropped from the tracker rather than never existing.
3. **Vocabulary mismatch.** `input_ineligible` (`src/protocol-v2.js:135`) vs the
   PRD's `ineligible_pre_dispatch` + `input_token_limit`
   (`bound-cheap-review-token-usage/prd.md:30-32`). Which wins?
4. **Does the park still hold?** `task.json:28` conditions resuming on v1 being
   distributed to fleet consumers *and* the v2 scope being revalidated. This run
   re-verified the reachability premise but did **not** probe fleet consumers for
   `config/routed-review-setup-v1.json` — that requires network access to the
   consumer repos. Unverified here.
5. **Which PR-Agent settings actually enforce limits?** Answering
   `bound-cheap-review-token-usage/prd.md:24-25` requires inspecting the pinned
   image `pragent/pr-agent@sha256:cae31b51b65b5c978a3b2a978d96e89e6a4c5bcd81cb2553fd8dad0251c3a23e`
   (`examples/pr-agent-router.yml:137`). Not done in this read-only pass.
6. **Manifest v5?** If any cost control needs consumer configuration, the
   installer needs a schema bump beyond `MANIFEST_SCHEMA_VERSION = 4`
   (`scripts/consumer-installer/codecs.mjs:159`). Whether cost policy belongs in
   the manifest at all, or entirely in the private catalog, is undecided.

## Recommendations

1. **Resolve the two missing children before sequencing anything.** The parent's
   own ordering requirement (`prd.md:82-84`) puts four children before
   `govern-cheap-review-fallbacks`. An ordering constraint referencing a
   non-existent task cannot be satisfied or falsified. Either recreate them or
   amend the PRD to the real three-child shape.
2. **Treat the distribution/reachability problem as the actual blocker.** The
   contracts these children need are ~90% written and 100% unreachable. Writing
   more unreachable contracts has negative value. The highest-leverage next step
   is one thin vertical slice that makes *one* cost control reach the Docker
   invocation, proving the catalog → compiler → adapter → workflow path
   end-to-end, before any child adds breadth.
3. **Start with the output cap.** Of the three children, the output token cap is
   the cheapest vertical slice: it is one environment variable on the Docker
   run, it needs no tokenizer, no pricing feed, and no evaluation set, and it
   directly buys the parent's "never counts length-limited partial output as
   completed assurance" criterion once paired with a finish-reason field on the
   acknowledgment. `enforce-cheap-provider-cost-policy` should go last of the
   three — it has the most external unknowns and the least existing code.
4. **Extend the acknowledgment before extending the ledger.** The parent's
   receipt criterion (configured vs actual model) is unmet and is a
   prerequisite for *every* cost measurement. `buildAdapterAcknowledgment`
   (`src/operations.js:242-259`) is 18 lines and reachable — it is the one place
   where a small change yields cross-child measurement.
5. **Reconcile vocabulary in the parent, once.** Pick `input_ineligible` or
   `ineligible_pre_dispatch` at the parent level and make all three children
   inherit it, rather than letting each child re-litigate.
6. **Add the v2 modules to `npm run check`.** The hardcoded list in
   `package.json` has drifted from `src/`. Prefer replacing the enumeration with
   a glob so it cannot drift again.
