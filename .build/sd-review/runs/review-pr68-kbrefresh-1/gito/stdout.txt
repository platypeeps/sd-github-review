        1: # SD GitHub Review Design
        2: 
        3: ## Purpose
        4: 
        5: `sd-github-review` is a routing action, not a hosted AI reviewer. It selects the
        6: least-expensive appropriate review level for a pull request and either requests
        7: GitHub Copilot or tells a consumer-owned workflow which external reviewer to
        8: run.
        9: 
        10: Deterministic CI, security scanners, branch protection, and human approval stay
        11: authoritative. AI review is supplemental.
        12: 
        13: ## Review Levels and Backends
        14: 
        15: | Route | Intended use | Action behavior | Backend status |
        16: | --- | --- | --- | --- |
        17: | `cheap` | Routine, lower-risk changes | Emits the configured cheap model and `run-external-reviewer=true` | Generic adapter plus executable PR-Agent workflow supported |
        18: | `deep` | Changes that need a more capable external review, including high-risk changes in the PR-Agent profile | Emits the configured deep model and `run-external-reviewer=true` | Generic adapter plus executable PR-Agent workflow supported |
        19: | `copilot` | Explicit native reviews only | Requests `copilot-pull-request-reviewer[bot]` through GitHub | Native integration supported |
        20: | `none` | Review intentionally disabled or event is irrelevant | Emits routing evidence without requesting a reviewer | Supported |
        21: 
        22: Copilot is the only reviewer backend invoked directly by the action. The
        23: `cheap` and `deep` routes are intentionally provider-neutral: the consuming
        24: workflow owns the reviewer runtime, credentials, prompt, and model-provider
        25: configuration.
        26: 
        27: The PR-Agent examples preserve that boundary with one provider selector, one
        28: provider-neutral API-key secret, and separate cheap/deep model IDs. They map
        29: the secret to one allow-listed single-key PR-Agent credential setting only on
        30: the container step. The step invokes the digest-pinned CLI image with
        31: `docker run` so the image retains its `/app` working directory; it passes
        32: credentials by environment-variable name and mounts no repository workspace.
        33: Provider expansion is an explicit workflow allowlist change; the router never
        34: receives a provider credential or constructs a secret name. Providers that
        35: also need endpoints, cloud identity, or additional configuration are outside
        36: this generic mapping contract.
        37: 
        38: The `copilot` route is not a named-model selection. GitHub chooses Copilot code
        39: review's model and does not expose model switching. GitHub separately offers
        40: Low and Medium review effort, but the review-request API used by this action
        41: has no effort parameter. Consequently, effort is neither selected per route
        42: nor represented in action outputs or durable receipts. A repository that uses
        43: GitHub automatic reviews for the same high-risk intent should normally choose
        44: Medium at the repository level; router-initiated requests must treat model and
        45: effort as GitHub-managed.
        46: 
        47: ## Architecture
        48: 
        49: The implementation follows one downhill dependency direction. Leaf utilities
        50: carry no policy; the versioned codecs depend only on those leaves; the route
        51: policy owner depends on the codecs; shared services and the two entrypoints
        52: depend on the policy owner. Codec and persistence layers never import policy.
        53: 
        54: 1. `src/path-match.js` is a leaf utility: pure glob→RegExp translation and
        55:    sensitive-file selection, with no routing knowledge.
        56: 2. `src/normalize.js` is a leaf utility: value canonicalizers (mode, escalation
        57:    route, confidence) and input parsers (list, review command, labels, trust,
        58:    event gating). These are canonicalization, not policy.
        59: 3. `src/protocol.js` validates and canonicalizes the versioned review request,
        60:    adapter request, backend, acknowledgment, successor, and receipt envelopes.
        61:    It also exposes `decodeRoutingInputs`, the codec seam that returns a fully
        62:    validated, typed routing-input record for the policy owner. It imports only
        63:    `normalize.js` and never any route policy.
        64: 4. `src/router.js` is the single route-policy owner. It holds the automatic
        65:    `routeReview` decision and the versioned `selectProtocolRoute` policy
        66:    (independent-review and risk floors, exact-head local-evidence reduction,
        67:    and trusted successor handling). It imports the `decodeRoutingInputs` codec
        68:    seam plus the leaf canonicalizers; it never imports codec internals.
        69: 5. `src/protocol.js` and `src/receipt.js` import no policy. `src/receipt.js`
        70:    persists and reconciles exact-head receipts in GitHub Check Runs and matches
        71:    bookkeeping paths through `path-match.js`, not the router.
        72: 6. `src/risk-context.js` builds the shared normalized routing context both
        73:    entrypoints feed to the policy owner. `src/reviewer-dispatch.js` runs the
        74:    shared Copilot presence probe and conditional reviewer request.
        75: 7. `src/operations.js` coordinates explicit `route`, `finalize`, and `query`
        76:    receipt operations plus the side-effect-free `acknowledge` adapter helper,
        77:    and emits bounded outputs. It builds context via `risk-context.js`,
        78:    dispatches via `reviewer-dispatch.js`, and routes via
        79:    `selectProtocolRoute`.
        80: 8. `src/index.js` selects standalone or durable orchestration and owns GitHub
        81:    output/error surfaces. Standalone stays policy-free: it builds context via
        82:    `risk-context.js`, dispatches via `reviewer-dispatch.js`, and calls
        83:    `routeReview` directly (never `selectProtocolRoute`).
        84: 9. `src/github.js` owns GitHub REST requests, pagination, reviewer requests,
        85:    comparison metadata, and Check Run transport. Consumer workflows still own
        86:    external reviewer adapters for `cheap` and `deep`.
        87: 
        88: ```mermaid
        89: flowchart TD
        90:     E["GitHub event and action inputs"] --> G{"Relevant routing event?"}
        91:     G -- "No" --> N["Emit none"]
        92:     G -- "Yes" --> P["Load required pull-request metadata"]
        93:     P --> X{"Fixed mode, trusted command, or route label?"}
        94:     X -- "Yes" --> R["Use explicit route"]
        95:     X -- "No" --> A["Evaluate draft, paths, size, and confidence"]
        96:     A --> D{"Selected route"}
        97:     R --> D
        98:     D -- "copilot" --> C["Deduplicate and request Copilot"]
        99:     D -- "cheap or deep" --> O["Emit model and external-reviewer signal"]
        100:     D -- "none" --> N
        101:     C --> S["Write outputs and step summary"]
        102:     O --> S
        103:     N --> S
        104: ```
        105: 
        106: Irrelevant events and explicit routes are resolved before pull-request file
        107: enumeration. This allows manual routing to work even for a pull request beyond
        108: GitHub's 3,000-file listing window and avoids unnecessary API use.
        109: 
        110: ### GitHub transport retry policy
        111: 
        112: The REST transport retries only `GET` requests, at most three total attempts.
        113: Transport failures and HTTP 408/429/500/502/503/504 use deterministic bounded
        114: backoff; HTTP 403 is eligible only when GitHub supplies primary- or
        115: secondary-rate-limit evidence. `retry-after` takes precedence, followed by a
        116: zero-remaining `x-ratelimit-reset`; a secondary limit without either waits 60
        117: seconds. No individual wait exceeds 60 seconds. A longer GitHub directive
        118: fails with bounded rate-limit context instead of retrying early.
        119: 
        120: Mutating requests are never retried. An interrupted reviewer request, Check
        121: Run create, or Check Run update therefore stays within the existing
        122: fail-closed reconciliation boundary and cannot be duplicated by transport
        123: recovery. Terminal API errors preserve the GitHub message and append only
        124: allow-listed rate-limit fields; authorization and arbitrary response headers
        125: are never logged.
        126: 
        127: ### Consumer installation lifecycle
        128: 
        129: Repository-only tooling under `scripts/` can provision the supported
        130: event-driven PR-Agent workflow in a separate consumer checkout. The installer
        131: copies the reviewed workflow unchanged, reconciles the bounded GitHub
        132: variables and routing labels, and passes the provider credential only through
        133: the `gh secret set` prompt or standard input. It never imports into the Action
        134: runtime, commits consumer changes, or stores a secret value.
        135: 
        136: `.github/sd-github-review.json` is the consumer-side ownership boundary. It
        137: records exact workflow/source hashes, provider/model configuration, and which
        138: GitHub resources the installer created. `pending`, `active`, and
        139: `uninstalling` states make interrupted GitHub mutations resumable. Updates and
        140: uninstalls refuse to overwrite a workflow whose current hash differs from the
        141: manifest; secrets and labels are preserved by default during removal because
        142: they may have other consumers.

        144: ## Durable On-Demand Workflow
        145: 
        146: `operation=standalone` preserves the event-driven behavior above. A trusted
        147: caller can instead provide one canonical v1 `review-request` and choose:
        148: 
        149: | Operation | Behavior |
        150: | --- | --- |
        151: | `route` | Revalidates the live PR head, selects policy, creates or reconciles one Check Run receipt, and performs at most one authorized dispatch |
        152: | `acknowledge` | Validates one adapter request and maps a bounded GitHub step outcome to canonical acknowledgment JSON; it performs no GitHub or provider call |
        153: | `finalize` | Validates one external adapter acknowledgment, revalidates the head, and advances that same receipt to failed or observed |
        154: | `query` | Reads one exact repository/PR/head/logical identity and never dispatches |
        155: 
        156: These operations, and `standalone`, are defined by one authoritative operation
        157: contract (`src/operation-contract.js`). It declares, per operation, whether the
        158: operation constructs a GitHub client/token, the inputs it reads, the outputs it
        159: emits, and the GITHUB_TOKEN permissions its own API calls require. Runtime
        160: decoding and `scripts/validate-action-metadata.mjs` both read that contract, so
        161: `action.yml`, the example workflows, `contract/routed-review-setup-v1.json`, and
        162: this document cannot drift from the runtime independently.
        163: 
        164: The durable identity is derived from repository, pull request, full head SHA,
        165: and attempt. Correlation IDs are aliases, not permission to dispatch again. A
        166: matching retry returns the existing receipt; a conflicting fingerprint fails;
        167: an uncertain mutation leaves the receipt in `reconciliation-required` with
        168: dispatch forbidden.
        169: 
        170: `acknowledge` is a workflow helper rather than a receipt operation exposed by
        171: setup discovery. It lets adapters such as PR-Agent record `success`, `failure`,
        172: `cancelled`, or `skipped` without accepting provider output or unbounded error
        173: text.
        174: 
        175: For Copilot, `route` checks both pending requests and non-dismissed reviews on
        176: the exact head before requesting. For `cheap` and `deep`, it emits one bounded
        177: `adapter-request`. The consumer-owned adapter writes findings to its declared
        178: review, comment, or check channels and returns one v1 acknowledgment. Only then
        179: does `finalize` complete the receipt. `none` records a skipped receipt without
        180: reviewer mutation.
        181: 
        182: Every new head has a distinct identity. Optional `supersedes` data is verified
        183: against the prior durable receipt and trusted GitHub comparison metadata. Raw
        184: paths are used only in memory; receipts retain a digest, counts, and normalized
        185: delta class. A bookkeeping-only successor may select `none` only in `auto`,
        186: when explicitly enabled and no independent-review floor overrides it.
        187: 
        188: Both published on-demand workflows expose that trusted repository policy
        189: directly. `rerequest-authorized` defaults to `false` and is enabled only for a
        190: validated attempt greater than one; `independent-review-floor` defaults to
        191: `none` and can require `cheap`, `deep`, or `copilot`. The two controls feed the
        192: initial route/query operation and never alter the canonical finalization
        193: identity.
        194: 
        195: [`contract/routed-review-setup-v1.json`](contract/routed-review-setup-v1.json)
        196: declares the workflow identity, contract major, supported intents and
        197: operations, Check Run capability, permissions, and immutable Action
        198: placeholder. Read-only clients combine that declaration with GitHub workflow
        199: metadata to classify `ready`, `absent`, `invalid`, `incompatible`, or
        200: `unavailable` before any dispatch.
        201: 
        202: `contract/` is where this repository publishes the reference descriptor;
        203: `config/routed-review-setup-v1.json` is the single path setup discovery probes
        204: in the repository being classified. The two are deliberately different: a
        205: reference copy on the probe path would make this repository classify itself as
        206: having the durable lane installed.

        208: ## Automatic Selection
        209:

        211:

        215: | 2 | Trusted exact `/review` command | Command route |
        216: | 3 | One explicit `review:*` label | Label route |
        217: | 4 | Draft and `review-drafts=false` | `none` |
        218: | 5 | A changed path matches `sensitive-paths` | `high-risk-route`, default `deep` |

        221: | 8 | No earlier rule matched | `cheap` |

        224: analysis step may provide `confidence=high`, `medium`, `low`, or `unknown`.

        153: ## Adopt a manually installed workflow
        154: 
        155: If you copied `examples/pr-agent-router.yml` into `.github/workflows/` by hand,
        156: `install` refuses to overwrite the unmanaged file. Use `adopt` to bring a
        157: recognized manual workflow under installer ownership without deleting it first:
        158: 
        159: ```sh
        160: node scripts/install-consumer.mjs adopt --target /path/to/consumer --dry-run
        161: node scripts/install-consumer.mjs adopt --target /path/to/consumer --yes
        162: ```
        163: 
        164: `adopt` recognizes only the current workflow template and an allow-list of
        165: previously shipped template versions, matched by exact content. It converges a
        166: recognized historical workflow to the current source, writes the ownership
        167: manifest (`pending` then `active`), and creates any missing managed variables,
        168: labels, or secret. It never claims pre-existing GitHub resources it did not
        169: create, so a later `uninstall` preserves them. Pass the same
        170: `--provider`/`--cheap-model`/`--deep-model` values your manual variables use; a
        171: conflicting unowned variable stops adoption before any mutation. Adoption
        172: requires confirmation (`--yes` for non-interactive runs). A workflow whose
        173: content is not a recognized template is rejected: back it up, remove it, and run
        174: `install` to reconcile manually. After adopting, `check`, `update`, and
        175: `uninstall` behave exactly as for a freshly installed consumer.
